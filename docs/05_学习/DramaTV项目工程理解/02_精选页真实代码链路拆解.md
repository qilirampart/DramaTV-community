# DramaTV 项目工程理解 - 第 2 课：精选页真实代码链路拆解

## 学习目标

本节结束后，你应该能做到：

- 看到 `/featured` 精选页时，不只知道它“能浏览资源”，还知道它背后经过哪些前端、接口、后端、数据库层级。
- 能解释精选页的分类、排序、搜索、滚动加载、返回定位为什么会牵涉多个模块。
- 能把以前熟悉的 `Controller / Service / DAO` 思路，对应到当前项目里的真实代码结构。
- 遇到“精选页数据不对、分类切换异常、加载慢、返回定位异常”时，能先判断应该查哪一层。

## 一句话总链路

精选页的真实链路可以先记成这一句：

```text
浏览器访问 /featured
-> Next.js 精选页组件维护筛选、瀑布流、缓存、返回定位
-> Next.js API Route 转发 /api/featured-inventory
-> Spring Boot Controller 接收 /api/feed/featured-inventory
-> HomeFeedQueryService 分发到 FeaturedInventoryQueryService
-> JdbcTemplate 查询 PostgreSQL
-> FeaturedInventoryResponse 返回给前端
-> 前端映射成瀑布流卡片并展示
```

这不是一个“页面文件自己展示假数据”的功能，而是一条完整的前后端数据链路。

## 1. 用户看到的是页面，代码入口是 `/featured`

用户打开的是：

```text
/featured
```

当前主要页面实现：

```text
apps/web/src/features/featured/FeaturedArchivePage.tsx
```

这个文件负责的事情比较多，不能只当成普通列表页看。它至少维护了这些状态：

- 当前一级分类：`all / workflow / video_prompt / image_prompt / activity`
- 当前排序：`hot / latest`
- 搜索词：`q`
- 二级筛选：工作流类型、提示词模型分类、提示词内容分类
- 当前已经加载的分页数据
- 下一页游标 `cursor`
- 瀑布流列数和卡片分配
- 资源真实宽高和卡片比例
- 返回详情页后的定位恢复
- sessionStorage / memory cache 中的页面快照

所以精选页后面出现过的很多问题，本质上不是“一个按钮点不了”这么简单，而是页面状态、路由参数、缓存、后端分页、瀑布流布局一起参与了结果。

## 2. 前端页面如何组装请求

精选页会把当前页面状态组装成一个查询对象。

关键代码位置：

```text
apps/web/src/features/featured/FeaturedArchivePage.tsx
```

重点函数：

```ts
buildFeaturedInventoryQuery(...)
requestFeaturedInventoryPage(...)
handleFeaturedInventoryPrefetchNextPage(...)
handleFeaturedInventoryLoadMore(...)
```

可以用这个简化模型理解：

```ts
{
  filter: "video_prompt",
  sort: "hot",
  q: "真人",
  modelCategory: "midjourney",
  contentCategory: "real-person",
  cursor: "offset:24",
  limit: 24
}
```

前端不会直接查数据库。它只负责根据页面状态拼出 API 查询参数，再通过 `fetch` 请求 Next.js 自己的 API Route。

## 3. Next.js API Route 是前端和后端之间的转发层

精选页相关的 Next.js API Route 有两个：

```text
apps/web/src/app/api/featured-inventory/route.ts
apps/web/src/app/api/public/featured-inventory/route.ts
```

它们的作用不是写业务查询，而是做三件事：

- 从浏览器请求里读取 `filter / sort / q / modelCategory / contentCategory / workflowType / cursor / limit`
- 调用 `apps/web/src/lib/api/featured-inventory.ts`
- 把 Spring Boot 返回的数据整理成前端可用的 JSON

两者差异：

- `/api/featured-inventory`：带登录态，响应头是 `private`，适合需要用户行为状态的场景，例如是否已点赞。
- `/api/public/featured-inventory`：不带登录态，响应头是 `public`，适合游客读取。

这一层可以理解成前端工程里的“接口代理层”，不是传统 Java 后端里的 Controller。

## 4. 前端接口封装层

关键文件：

```text
apps/web/src/lib/api/featured-inventory.ts
```

它的主要职责：

- 统一调用社区后端的精选库存接口。
- 设置请求超时时间，目前是 `8000ms`。
- 后端不可用时提供可降级的空数据结构。
- 复用查询参数归一化逻辑。

关键函数：

```ts
getFeaturedInventory(...)
getOptionalFeaturedInventory(...)
getPublicFeaturedInventory(...)
getOptionalPublicFeaturedInventory(...)
```

你可以把这一层理解为前端的“后端 API 客户端”。它不决定查哪些表，只决定怎么请求后端、失败时怎么兜底。

## 5. Spring Boot Controller 才是后端 API 入口

后端入口：

```text
apps/server/src/main/java/com/dramatv/community/feed/controller/HomeFeedController.java
```

精选库存接口：

```java
@GetMapping("/featured-inventory")
public ResponseEntity<ApiResponse<FeaturedInventoryResponse>> featuredInventory(...)
```

真实 HTTP 路径：

```text
GET /api/feed/featured-inventory
```

它接收的参数包括：

- `filter`
- `sort`
- `q`
- `modelCategory`
- `contentCategory`
- `workflowType`
- `limit`
- `cursor`

Controller 在这里不直接写 SQL。它只做入口接收，然后调用：

```java
homeFeedQueryService.loadFeaturedInventory(...)
```

这和你以前学的 Java Web 思路是对得上的：

```text
Controller = 接收 HTTP 请求的入口层
```

## 6. Application 层相当于当前项目里的 Service

关键文件：

```text
apps/server/src/main/java/com/dramatv/community/feed/application/HomeFeedQueryService.java
```

这里的 `application` 包，可以先按你熟悉的 `service` 来理解。

`HomeFeedQueryService` 在精选页链路里主要负责分发：

```java
return featuredInventoryQueryService.loadInventory(...);
```

它自己不展开精选页复杂查询，而是把更细的查询交给：

```text
FeaturedInventoryQueryService
```

这说明当前项目不是严格按“Controller / Service / DAO”三个固定文件夹机械分层，而是按业务域组织：

```text
feed
├─ controller
├─ application
├─ dto
```

在 `application` 下面，既可能有普通业务服务，也可能有专门查询服务。

## 7. 当前精选页最接近 DAO 的层是 `FeaturedInventoryQueryService`

关键文件：

```text
apps/server/src/main/java/com/dramatv/community/feed/application/FeaturedInventoryQueryService.java
```

这个类虽然放在 `application` 包下，但它直接持有：

```java
private final JdbcTemplate jdbcTemplate;
```

它直接写 SQL、拼查询条件、映射 ResultSet，所以从你以前学过的分层角度看，它承担了很大一部分 `DAO / Repository / QueryService` 的职责。

更准确地说：

```text
传统 DAO 的“查数据库”职责
在当前精选页链路里主要落在 FeaturedInventoryQueryService + JdbcTemplate 上。
```

这个类做的事情包括：

- 校验并归一化 `filter / sort / limit / cursor`
- 计算分类数量 `summary.counts`
- 计算提示词模型和内容分类的 facet 数量
- 查询视频提示词
- 查询图片提示词
- 查询工作流
- 在 `all` 分类下混合视频、图片、工作流
- 根据 `hot / latest` 排序
- 用 `offset:<number>` 做滚动分页游标
- 解析媒体资源 URL
- 返回前端需要的卡片字段

## 8. 精选页后端分页是怎么做的

当前后端分页参数：

```java
private static final int DEFAULT_LIMIT = 24;
private static final int MAX_LIMIT = 48;
private static final String OFFSET_CURSOR_PREFIX = "offset:";
```

默认一次拉 24 条，最大允许 48 条。

游标长这样：

```text
offset:24
offset:48
offset:72
```

简化理解：

```text
第一次请求：cursor 为空，offset = 0，返回 0-23 条
第二次请求：cursor = offset:24，返回 24-47 条
第三次请求：cursor = offset:48，返回 48-71 条
```

这解释了为什么之前做“滚动加载”和“返回定位”时，问题容易变复杂：

- 如果返回定位的目标卡片在第 300 条，前端必须恢复足够多的分页数据，否则 DOM 里根本没有那个卡片。
- 如果瀑布流布局还没稳定，即使数据到了，卡片位置也可能还没稳定。
- 如果 hash 锚点没有被清理，后续滚动加载时可能反复跳回旧卡片。

## 9. `all` 分类不是简单查一张表

`all` 分类的特殊点是混合展示。

后端会分别查询：

- 视频提示词
- 图片提示词
- 工作流

然后通过 `buildMixedAllCandidates(...)` 合并。

这就是为什么之前你看到“全部页后面图片优先、视频不混合”时，不能只查前端 UI。真正决定混合策略的是后端 `FeaturedInventoryQueryService` 里的候选合并逻辑。

简化链路是：

```text
queryPromptCandidates("video_prompt")
queryPromptCandidates("image_prompt")
queryWorkflowCandidates(...)
-> pickNextAllCandidate(...)
-> buildAllCursorPage(...)
```

## 10. 搜索不是简单只搜标题

精选页搜索会查多个字段。

提示词搜索覆盖：

- `prompt.title`
- `prompt.summary`
- `prompt.prompt_text`
- `prompt.prompt_text_zh`
- `prompt.prompt_text_en`
- `prompt.prompt_text_raw`
- 作者名
- 标签
- `model_category`
- `content_category`
- `composition_category`

并且目前有少量语义扩展，例如：

```text
真人 -> real-person
动画 -> animation
```

所以你之前提到“搜真人，结果质量一般”，对应的真实优化点不是只改输入框，而是要看：

- 查询字段是否覆盖足够
- 分类字段是否正确
- 导入数据的 taxonomy 是否准确
- 是否需要更强的同义词表或搜索索引
- 是否需要从 `LIKE` 升级到 PostgreSQL 全文搜索或向量检索

## 11. DTO 决定后端返回给前端什么

关键文件：

```text
apps/server/src/main/java/com/dramatv/community/feed/dto/response/FeaturedInventoryResponse.java
```

核心结构：

```java
public record FeaturedInventoryResponse(
        Summary summary,
        CursorPageResponse<Item> page
) {}
```

前端拿到的数据大体是：

```text
summary：分类数量、筛选项数量
page.items：当前页卡片列表
page.nextCursor：下一页游标
page.hasMore：是否还有下一页
```

单个卡片 `Item` 里包含：

- 内容类型：`contentKind / promptModality / itemType`
- 目标 ID：`targetId`
- 标题和简介：`title / summary`
- 媒体资源：`coverUrl / posterUrl / previewUrl / sourceUrl`
- 宽高：`width / height`
- 作者：`author`
- 统计：`stats`
- 标签：`tagNames`
- 分类字段：`modelCategory / contentCategory`
- 用户行为：`viewerActions`

DTO 可以理解为“后端对前端承诺的数据结构”。如果页面需要一个字段，通常要看 DTO 里有没有，再看 QueryService 有没有查出来。

## 12. 数据库层依赖哪些表

精选页最核心的表包括：

- `prompt_entries`：视频提示词和图片提示词的内容真相表。
- `workflows`：工作流内容表。
- `users`：作者信息。
- `media_assets`：封面、预览、源文件等媒体资源。
- `interaction_actions`：点赞等用户行为。

辅助相关：

- `discussion_threads`：帖子，目前不应该混入精选页提示词资源流。
- `discussion_channels`：帖子频道。

这里要建立一个关键认识：

```text
前台看到的一个精选卡片，不一定来自一张表。
它可能是 prompt_entries + users + media_assets + interaction_actions 组合出来的结果。
```

所以排查“卡片封面不对、作者不对、点赞状态不对、分类不对”时，要分别看不同表和不同 join。

## 13. 精选页瀑布流为什么容易出问题

精选页现在不是普通等高网格，而是瀑布流。

前端需要根据资源比例决定卡片高度：

```text
width / height -> aspectRatio -> masonry column assignment
```

如果资源宽高暂时未知，前端会先用 fallback 比例，再等待图片或视频元信息稳定。这个过程会导致视觉上“先抖一下再稳定”。

因此你提出的“提前加载一批资源，避免用户看到变化过程”是合理的。它本质上是在做：

- 数据预取
- 媒体尺寸预热
- 瀑布流布局提前稳定
- 用户滚动到底部前就把下一批准备好

但它不能无限预取，否则会增加后端压力和浏览器内存压力。当前项目里比较合理的是“接近底部时预取下一页，真正到底部附近再提交到列表”。

## 14. 返回定位为什么牵涉这么多模块

精选页返回定位至少涉及：

- 路由 hash，例如 `#featured-item-xxx`
- sessionStorage 页面快照
- memory cache
- 已加载分页数据
- 瀑布流列分配
- 卡片真实比例
- 浏览器 scroll restore
- 详情页返回来源 `backSource`

所以这个功能不是简单一句：

```ts
window.scrollTo(...)
```

真正可靠的返回定位要满足：

- 数据先恢复到足够多，目标卡片必须在 DOM 里。
- 瀑布流布局先稳定，否则滚动位置会漂。
- 只定位一次，不能在后续加载更多时反复跳回旧锚点。
- 从详情页、作者页、多层返回时，来源页面的状态不能互相污染。

这也是为什么之前反复出现“返回后左侧列不显示”“定位加载卡死”“继续下滑又跳回旧资源”这类问题。它们不是孤立 bug，而是返回定位策略、分页恢复、瀑布流布局三者之间的协作问题。

## 15. 遇到精选页问题时应该怎么查

### 分类切换内容不对

优先检查：

```text
FeaturedArchivePage.tsx
-> 当前 URL 参数是否正确
-> Next.js API Route 收到的 filter/sort 是否正确
-> HomeFeedController 参数是否正确
-> FeaturedInventoryQueryService 是否按 filter 查询
-> 数据库 taxonomy 字段是否正确
```

### 后台配置和前台展示不一致

优先检查：

```text
后台配置是否写入正确表
-> 前台调用的是运营配置接口还是库存接口
-> 后端是否有缓存或降级数据
-> 前端是否命中 session/memory cache
-> 云端 release 是否真的更新
```

### 下滑加载慢或不加载

优先检查：

```text
IntersectionObserver 是否触发
-> cursor 是否正确传递
-> 后端 hasMore / nextCursor 是否正确
-> 网络请求是否失败或超时
-> 瀑布流渲染是否被大量卡片阻塞
```

### 返回定位卡死

优先检查：

```text
目标卡片 ID 是否存在
-> 目标分页是否已恢复
-> 后端是否还能继续返回下一页
-> 瀑布流布局是否完成
-> hash 是否被重复消费
-> sessionStorage 快照是否过期或污染
```

### 搜索质量不够

优先检查：

```text
搜索词是否进入 q 参数
-> appendPromptSearchClause 覆盖字段是否足够
-> taxonomy 字段是否准确
-> 是否需要同义词扩展
-> 是否要升级搜索索引
```

## 16. 用旧知识映射当前项目

你以前学过的分层大概是：

```text
Controller -> Service -> DAO -> Database
```

当前精选页可以这样对应：

```text
HomeFeedController
-> HomeFeedQueryService
-> FeaturedInventoryQueryService
-> JdbcTemplate
-> PostgreSQL
```

再加上前端后，完整链路是：

```text
Next.js Page
-> Next.js API Route
-> Spring Controller
-> Application / QueryService
-> JdbcTemplate
-> PostgreSQL
```

所以你看到当前项目里不是每个功能都有单独 `dao` 文件夹，不代表没有数据访问层。只是这个项目的部分查询把 DAO 职责放进了专门的 QueryService。

## 17. 本节小结

- 精选页是一个很好的学习样本，因为它同时包含前端状态、接口参数、后端查询、数据库 join、分页、缓存、瀑布流和返回定位。
- 当前项目的 `application` 包大致对应你熟悉的 Service 层，但其中的 `FeaturedInventoryQueryService` 同时承担了 QueryService / DAO 的职责。
- DTO 是后端对前端的数据契约，`FeaturedInventoryResponse` 决定了精选页能展示什么字段。
- 如果精选页展示异常，不要先猜 UI，要按“页面状态 -> API 参数 -> Controller -> QueryService -> SQL -> 数据表 -> 前端缓存和布局”顺序排查。
