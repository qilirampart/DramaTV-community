# DramaTV 项目工程理解 - 第 5 课：Git 基础：工作区、暂存区、提交、分支到底是什么

## 学习目标

本节结束后，你应该能做到：

- 说清楚 `工作区`、`暂存区`、`提交 commit`、`分支 branch` 分别是什么。
- 知道为什么 Git 是你和 AI 协作时的安全带。
- 知道 `git status`、`git diff`、`git add`、`git commit` 最核心是在保护什么。
- 能把 DramaTV 当前仓库的真实脏工作区，映射到 Git 的几个概念上。

## 1. 为什么你现在必须学 Git

你当前不是在写一个很小的 demo，而是在维护一个真实项目：

- 前台 `apps/web`
- 后台 `apps/admin`
- 后端 `apps/server`
- 大量脚本 `scripts`
- 发布脚本、回滚脚本、进度文档、学习文档

而且你现在大量使用 AI 协作改代码。

这会带来一个现实问题：

```text
你不一定每一行代码都手写
但你必须知道这次到底改了什么
哪些改动是我的
哪些改动是别人的
哪些能提交
哪些不能提交
出问题时怎么退
```

Git 就是在解决这个问题。

所以对你来说，Git 不是“开发者仪式”，而是：

```text
保护现场
识别改动
组织版本
控制风险
支持回滚
```

## 2. 最核心的四层概念

你可以先把 Git 理解成四层：

```text
工作区
-> 暂存区
-> 提交历史
-> 分支
```

### 工作区

工作区就是你当前磁盘上的真实文件。

只要你改了文件但还没提交，这些改动就在工作区里。

你可以把工作区理解成：

```text
你正在编辑的真实现场
```

### 暂存区

暂存区是“准备进入下一次提交的改动清单”。

它表示：

```text
这些改动我准备打包成一次提交
```

常见命令：

```bash
git add <file>
```

意思不是“提交了”，而是：

```text
把这部分改动放进下一次提交的候选包里
```

### 提交 commit

提交是一次被记录下来的版本快照。

它的本质是：

```text
把暂存区当前那一批改动，正式记录进历史
```

### 分支 branch

分支可以先理解成：

```text
一条独立演进的版本线
```

比如常见的：

```text
main
dev
feature/xxx
```

## 3. 用现实类比理解四层

你可以先这样类比：

```text
工作区 = 你桌上正在修改的纸稿
暂存区 = 你准备装进这次文件袋的页面
提交 = 这次正式归档入库的一份版本
分支 = 不同主题或不同阶段的归档线
```

真正顺序是：

```text
先在工作区修改
-> 选择其中一部分放入暂存区
-> 再 commit 形成历史版本
```

## 4. `git status` 在看什么

`git status` 回答的问题是：

```text
现在仓库相对于上一次提交，变成什么样了？
```

它通常会告诉你：

- 当前在哪个分支。
- 哪些文件改了但还没暂存。
- 哪些文件已经暂存。
- 哪些新文件还没被 Git 跟踪。

所以：

```text
git status 的价值是先确认现场
```

## 5. `git diff` 在看什么

`git diff` 回答的问题是：

```text
具体改了哪几行？
```

区别是：

```text
git status 看“哪些文件变了”
git diff   看“文件里面怎么变了”
```

## 6. `git add` 真正做了什么

`git add` 不是“上传”，不是“提交”，也不是“同步远端”。

它只是在做一件事：

```text
把你选中的改动放进暂存区
```

所以在脏工作区里，最危险的动作之一就是无脑：

```text
git add .
```

因为这可能把很多不该一起提交的改动都打包进去。

## 7. `git commit` 真正做了什么

`git commit` 会把暂存区里的那一批内容，变成一个正式历史节点。

重点不是“按按钮”，而是：

```text
这次提交到底在表达一个什么改动意图？
```

好的 commit 至少要满足：

- 改动主题相对单一。
- 信息可解释。
- 出问题时容易回滚。
- 不把无关文件混进去。

## 8. 分支在当前项目里的意义

对 DramaTV 当前项目，先记住：

```text
main = 更稳定、更收敛的主线
dev  = 当前主要开发演进线
```

分支的意义是：

- 不同阶段的代码可以分开推进。
- 未验证的东西不要直接混进主线。
- 需要回看历史时更清楚“这段时间是在做什么”。

## 9. Git 为什么是 AI 协作的安全带

AI 写代码时，最危险的不是“不会写”，而是：

- 改多了你没看见。
- 改到了不该改的文件。
- 覆盖了你或别人已有改动。
- 修一个点时顺手动了别的区域。
- 最后说不清这轮到底动了什么。

Git 能提供三层保护：

```text
status：先看现场
diff：看清改动内容
commit：把确认过的改动封装成可追踪版本
```

## 10. 对 DramaTV 当前仓库的现实提醒

这个仓库现在是典型脏工作区。

这意味着：

- 不能默认“所有改动都是这一轮的”。
- 不能默认“所有改动都应该提交”。
- 不能默认“可以一键加所有文件”。

这时最危险的动作往往是：

```text
git add .
git commit -m "update"
```

因为这很可能把：

- 业务代码
- 部署脚本
- 文档
- 备份文件
- 临时文件
- 别人的改动

一起打包进去。

所以在这个项目里，Git 的第一价值不是“发版本”，而是：

```text
隔离改动
避免误伤
提高可解释性
```

## 11. 当前最该掌握的最小 Git 动作

先不用学太多命令，先把这几个动作吃透：

```text
git status
git diff
git add <file>
git commit -m "..."
```

它们分别回答：

```text
现在乱成什么样了？
具体改了什么？
我准备提交哪一部分？
我要把这批改动记成什么版本？
```

## 12. 本节小结

- 工作区是当前真实文件现场。
- 暂存区是“准备进入下一次提交的改动包”。
- commit 是把暂存区正式记入历史。
- branch 是不同历史演进线。
- `git status` 先看现场，`git diff` 再看细节。
- `git add` 不是提交，而是选择“这次要提交什么”。
- 在 AI 协作和脏工作区下，Git 首先是风险控制工具，不只是版本工具。
