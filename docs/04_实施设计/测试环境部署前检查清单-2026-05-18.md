# 测试环境部署前检查清单

日期：`2026-05-18`

适用范围：

- 社区前台测试环境部署
- 社区后端测试环境部署

## 1. 先确认这次到底改了什么

部署前先把改动归类清楚：

- 只改前台
- 只改后端
- 前后端都改了
- 是否涉及共享层
  - 登录
  - 发布
  - 评论
  - 通知
  - 举报
  - 权限

如果涉及共享层，不要只看单页效果。

## 2. 本地最低验证要求

### 2.1 默认必跑

```powershell
npm run deploy:verify:pre
```

当前等价于：

```powershell
npm run verify:quick
```

### 2.2 建议补跑

如果这轮改动较大，建议再跑：

```powershell
npm run verify:full
```

## 3. 按改动类型追加检查

### 3.1 改前台时

至少确认：

- `npm run typecheck:web`
- `npm run smoke:web`

### 3.2 改后台前端时

至少确认：

- `npm run typecheck:admin`
- `npm run smoke:admin`

### 3.3 改后端时

至少确认：

- `npm run backend-test`

如果改的是读链路、后台治理或日志链路，按需补：

- `npm run backend-test:read`
- `npm run backend-test:admin`
- `npm run backend-test:logging`

## 4. 发布前的同步判断

部署前明确这次需要同步什么：

- 只同步本机 `3107` 云镜像前端
- 同步公网前台
- 同步云后端
- 是否还要同步数据库变更
- 是否有脚本、配置或文档也要一起落库

不要出现“代码改了，但部署对象没改对”的情况。

## 5. 配置与环境检查

如果这轮改动涉及环境依赖，再额外确认：

- 数据库连通
- Redis 连通
- OSS 配置
- Nginx / 代理层配置
- 测试账号是否可用

## 6. 部署前人工确认项

至少确认下面几项：

1. 这轮改动已在本地看过
2. 本地自动化验证已通过
3. 知道要部署前台、后端还是两者
4. 知道部署失败时回滚到哪个 release

## 7. 建议口径

最稳妥的部署前顺序：

1. 本地完成改动
2. 跑 `npm run deploy:verify:pre`
3. 必要时跑 `npm run verify:full`
4. 明确部署对象
5. 再执行测试环境部署

## 8. 版本管理补充

部署前再补一条：

```powershell
npm run release:list:test
```

确认两件事：

1. 当前 `current` 指向的是哪一版
2. 如果这次部署失败，准备回退到哪一版

稳定版本台账统一记在：

- `ops/releases/test-env-release-ledger.md`
