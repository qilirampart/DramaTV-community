# 测试环境部署回滚与故障排查清单

日期：`2026-05-18`

适用范围：

- 社区前台测试环境
- 社区后端测试环境
- 当前 ECS 测试机：`8.141.20.130`
- 社区前台默认公网入口：`http://community.8.141.20.130.nip.io`
- 管理后台默认公网入口：`http://community.8.141.20.130.nip.io/admin`
- `http://8.141.20.130` 只作为机器原始公网 IP 使用，不作为社区默认业务入口

当前真实部署对象：

- 前台服务：`dramatv-community-web.service`
- 后端服务：`dramatv-community-server.service`
- 前台部署脚本：`scripts/deploy-test-web.ps1`
- 后端部署脚本：`scripts/deploy-test-backend.ps1`

## 1. 标准部署口径

建议顺序：

1. 部署前执行：`npm run deploy:verify:pre`
2. 执行部署脚本
3. 部署后执行：`npm run deploy:verify:post:test`
4. 如有必要，再补浏览器级人工验收

如果希望部署脚本内直接带验证，可使用：

- 前台：`scripts/deploy-test-web.ps1 -VerifyBeforeDeploy -VerifyAfterDeploy`
- 后端：`scripts/deploy-test-backend.ps1 -VerifyBeforeDeploy -VerifyAfterDeploy`

## 2. 部署失败先看什么

### 2.1 前台部署失败

先查：

- 本地 `npm run deploy:verify:pre` 是否已通过
- `scripts/deploy-test-web.ps1` 控制台输出停在：
  - 打包
  - 上传
  - 远端 `npm ci`
  - 远端 `npm run build`
  - `nginx -t`
  - `systemctl restart dramatv-community-web.service`

优先排查点：

- 本地前端构建是否已坏
- 远端 Node 版本或依赖安装是否异常
- Nginx 配置是否未通过
- 前台服务是否启动但未监听 `3106`

### 2.2 后端部署失败

先查：

- 本地 `npm run deploy:verify:pre` 是否已通过
- `scripts/deploy-test-backend.ps1` 控制台输出停在：
  - 本地 `package`
  - 上传 jar
  - 上传 env
  - `systemctl restart dramatv-community-server.service`
  - `/actuator/health`

优先排查点：

- 本地 Maven 打包是否已坏
- ECS 到 PostgreSQL / Redis 是否已断
- ECS RAM Role / OSS 配置是否异常
- 后端服务是否启动但没有通过健康检查

## 3. 服务异常时的最短检查顺序

### 3.1 前台打不开

按这个顺序查：

1. `http://community.8.141.20.130.nip.io/` 是否 `200`
2. ECS 上 `dramatv-community-web.service` 是否 `active (running)`
3. `curl -I http://127.0.0.1:3106`
4. `nginx -t`
5. `curl -I http://127.0.0.1/`

如果 `127.0.0.1:3106` 正常但公网不正常，优先怀疑：

- Nginx 配置
- Nginx reload 未生效
- 80 端口入口异常

### 3.2 前台可开但接口异常

按这个顺序查：

1. `curl http://127.0.0.1:18080/actuator/health`
2. `curl http://127.0.0.1:18080/api/feed/home`
3. `curl http://127.0.0.1/api/feed/home`
4. 再看前端页面是否只是代理层异常

### 3.3 后端服务异常

按这个顺序查：

1. `systemctl --no-pager --full status dramatv-community-server.service`
2. `journalctl -u dramatv-community-server.service -n 120 --no-pager`
3. `curl http://127.0.0.1:18080/actuator/health`
4. 再确认数据库 / Redis 连通

## 4. 回滚动作

### 4.1 前台回滚

当前前台发布目录结构：

- `/opt/dramatv-community-web/releases/<timestamp>`
- `/opt/dramatv-community-web/current`

回滚原则：

- 找到上一个已知正常的 release
- 把 `current` 软链切回旧 release
- 重启 `dramatv-community-web.service`
- 再跑 `npm run deploy:verify:post:test`

回滚后至少检查：

- `/`
- `/login`
- `/api/feed/home`

### 4.2 后端回滚

当前后端发布目录结构：

- `/opt/dramatv-community-server/releases/<timestamp>`
- `/opt/dramatv-community-server/current`

回滚原则：

- 找到上一个已知正常的 jar release
- 把 `current/dramatv-community-server.jar` 的软链切回旧 jar
- 重启 `dramatv-community-server.service`
- 先查 `/actuator/health`
- 再跑 `npm run deploy:verify:post:test`

回滚后至少检查：

- `/actuator/health`
- `/api/feed/home`
- `/api/prompts?modality=all&limit=1`
- `/api/discussions/home`

## 5. 现在这套链路的已知风险

### 5.1 公网验收不一定每次都能稳定跑通

当前已经验证过：

- `check-test-runtime-readiness.mjs` 在本地链路是正常的
- 但从当前机器直探 `http://community.8.141.20.130.nip.io/` 仍可能拿到 `502` 或超时

这意味着：

- `deploy:verify:post:test` 失败时，不能直接下结论是脚本错
- 还要区分：
  - 当前机器到公网入口不稳定
  - Nginx / 服务本身异常
  - 内外网切换导致的网络可达性问题

### 5.2 当前部署仍然偏“人工触发”

当前已经有：

- 统一验证入口
- 部署前后固定动作
- 回滚目录结构

但还没有：

- CI 自动触发
- 自动记录成功版本到单独 release manifest
- 一键回滚脚本

所以现在最稳妥的策略仍然是：

- 先本地验证
- 再手工部署
- 再手工确认关键页

## 6. 推荐的最小人工验收页

前台至少看：

- `/`
- `/login`
- `/featured`
- `/discussions`

后端至少查：

- `/actuator/health`
- `/api/feed/home`
- `/api/prompts?modality=all&limit=1`
- `/api/discussions/home`
