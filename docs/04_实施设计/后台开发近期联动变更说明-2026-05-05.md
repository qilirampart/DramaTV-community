# 后台开发近期联动变更说明

更新时间：2026-05-05

## 1. 目的

这份文档用于给 `DramaTV` 社区后台开发线做交接。

重点不是重写后台规划，而是把最近几天已经落地、并且会直接影响后台继续开发的改动集中说明，避免后台继续按旧认知接接口、接页面或重复造数据结构。

当前时间窗主要覆盖：

- `2026-04-28` 到 `2026-05-05`

## 2. 当前前后台拆分现状

当前项目已经固定为前后台分离开发，但共用同一套社区后端和同一套社区数据：

- 社区前台：`apps/web`
- 后台前端：`apps/admin`
- 社区/后台共享后端：`apps/server`

当前约定：

- 后台本地开发端口：`3206`
- 后台接口统一走：`/api/admin/**`
- 后台不是单独再起一套社区业务库，而是直接复用社区真实内容、评论、审核、举报、用户数据

这意味着后台开发时要特别注意两点：

1. 后台不要再单独定义一套“后台专属内容对象”
2. 后台要尽量直接消费社区已经落地的真实表和真实状态流转

## 3.2 后台前端已有页面里，真接入和占位页要区分清楚

当前 `apps/admin` 里页面状态已经进一步统一。

已经接到真实后端的页面：

- `users`
- `comments`
- `moderation`
- `reports`
- `taxonomy`
- `feed-ops/home`
- `feed-ops/featured`
- `feed-ops/discussions`

仍然主要是占位壳或静态参考页的页面：

- `media-tasks`
- `audit-logs`
- `dashboard/overview`
- `users` 详情能力仍未补齐

其中最重要的现状差异是：

- `reports` 已经接成真实工单中心，但关闭语义和文案仍可继续收口
- `taxonomy` 已经接成真实可写治理链路，启停 / 排序 / 曝光开关 / 备注已可真实保存
- `feed-ops/home / featured / discussions` 已经全部接成真实配置读写，三页统一复用同一个 page-definition 运营编辑器
- 真正还停在参考壳阶段的，主要剩 `media-tasks / audit-logs / dashboard/overview / users detail`

这会直接影响后台接下来的优先级：后续不该再重复补 `reports` 的静态壳，而应转向 `feed-ops/featured / feed-ops/discussions / media-tasks / audit-logs` 的剩余真链路。

## 3.3 前台举报提交流程已经落地为真实数据

最近社区主线已经完成真实举报链路，不再是占位按钮。

真实入口：

- `POST /api/reports`

当前行为：

- 需要登录
- 支持举报目标：`video / workflow / prompt / post`
- 支持原因枚举：
  - `pornographic`
  - `political`
  - `spam`
  - `abuse`
  - `copyright`
  - `misleading`
  - `other`
- 会校验目标是否真实存在
- 会写入 `report_tickets`
- 新建工单默认状态：`pending`
- 同一用户对同一目标，若已存在 `pending / processing` 工单，则禁止重复提交
- 重复提交会返回：`REPORT_DUPLICATE`

后台侧补充说明：

- `admin/reports` 已直接以 `report_tickets` 为主数据源承接这条链路
- 虽然公开 `/api/reports` 目前主文档写的是 `video / workflow / prompt / post`，但后台 `reports` 侧已经兼容现有库里的 `comment` 工单
- 评论类举报在后台不走 `moderation.offline(...)`，而是联动 `admin/comments.hideComment(...)`

对后台开发的影响：

- 后台举报中心不应该再自建新表
- 后台应直接以 `report_tickets` 为主数据源
- 这一条已不再是“待承接方向”，而是已经落地的真实举报工单治理页

## 3.4 审核池已补齐帖子，不再只有作品类内容

之前有一个真实缺口：

- 帖子发布后没有进入 `audit_records`

现在这个缺口已经补齐：

- 帖子发布时也会写入 `audit_records`

当前审核池已可覆盖：

- 视频作品
- 提示词
- 工作流
- 帖子

对后台开发的影响：

- 后台审核中心现在可以统一做跨内容类型治理
- 后台不需要为了帖子单开一套完全平行的审核池
- `moderation` 页后续如果继续扩展筛选器，应按 `targetType` 做统一治理视图

## 3.5 Prompt taxonomy 已进入后端正式字段

最近已经新增数据库迁移：

- `V19__add_prompt_taxonomy_fields.sql`

已给 `prompt_entries` 增加字段：

- `model_category`
- `content_category`
- `composition_category`

并且这些字段已经进入后端查询与发布落库流程，不再只是前端猜标签。

对后台开发的影响：

- 后台的 `taxonomy` 页面后续应直接围绕这三个正式字段设计
- 后台不要继续依赖前端 mock 标签或仅靠 `tagNames` 推断分类
- 后续做分类治理、批量修正、筛选统计时，应以这三个字段为核心
- 当前 `admin/taxonomy` 已直接把这三个字段接成真实治理链路：
  - 分类统计、分类项列表、覆盖作者数、最近发布时间、样例标题都来自真实 `prompt_entries`
  - 启停、排序、曝光开关、治理备注通过 `admin_taxonomy_configs` 做 overlay 写入
  - 写接口只允许治理真实存在的 taxonomy 项，不额外造第二套分类体系

## 4. 后台开发当前最该注意的“错位点”

## 4.1 之前最大的 reports 错位已经补齐，但状态语义还没完全收口

之前最明显的错位是：

- 前台已经能产生 `report_tickets`
- 后台 `reports` 页当时还在展示静态样例数据

这个错位现在已经补齐：

- `reports` 列表、详情、处理中、关闭、联动下线、联动隐藏评论都已走真后端
- 浏览器运行态已经验到 `标记处理中 / 联动下线内容 / 关闭工单`

当前还需要注意的不是“有没有真接口”，而是状态语义和文案是否完全收口：

- 当前 `close` 动作对 `pending / processing` 工单会先落到 `resolved`
- 页面上对应展示为 `已处理`
- 如果后续产品要把“关闭工单”严格等同于 `closed`，需要继续收口按钮文案和状态流转

## 4.2 moderation 和 reports 不能混成一页数据概念

当前两个池子的职责要分清：

- `moderation` 更偏“内容审核池”
- `reports` 更偏“用户举报工单池”

二者可以联动，但不应混成一张表或一套状态。

更合理的关系是：

- `reports` 负责接收举报事实、处理工单、沉淀证据
- `moderation` 负责对内容执行通过、驳回、下线、恢复等治理动作

后台开发时不要把举报页直接做成另一个审核页壳子。

## 4.3 taxonomy 已进入真实治理链路

虽然 `taxonomy` 页的治理位已经可写，但当前真正稳定下来的 taxonomy 核心字段仍然只有：

- `model_category`
- `content_category`
- `composition_category`

当前已落地部分：

- 实时分类统计
- 分类项列表
- 分类项详情视图
- 启停 / 排序 / 曝光开关 / 治理备注真实写入
- 覆盖作者数 / 最近发布时间 / 样例标题

因此后台后续如果继续扩 taxonomy，建议优先围绕：

- 内容筛选与批量修正
- 发布页/精选页分类口径统一

而不是先做过重的树状可视化配置。

## 5. 建议后台下一步优先承接的事项

建议后台接下来按这个顺序推进：

1. `feed-ops` 继续把 `featured / discussions` 接成真实排序配置
2. `media-tasks` 接异步任务与媒体处理状态
3. `audit-logs` 接真实审计日志或先明确日志来源边界
4. `taxonomy` 继续补批量修正和筛选治理
5. `reports` 继续收口状态语义与按钮文案

其中第 1 条优先级当前更高，因为：

- `feed-ops/home` 已经有真实读写样板，继续补 `featured / discussions` 的切入最顺
- `media-tasks / audit-logs` 仍然整体停在参考壳阶段
- `reports` 虽然还有语义细节可调，但主治理链路已经不再断开

## 6. 开发时的几个注意事项

## 6.1 以真实表和真实状态为准

后台继续开发时，优先复用这些真实对象：

- `users`
- `comments`
- `audit_records`
- `report_tickets`
- `prompt_entries`
- `media_assets`
- `async_task_records`

不要为方便出页面，再平行造一套临时后台表。

## 6.2 小心“本地跑着旧 runtime”造成误判

最近浏览器复检时已经出现过一次典型问题：

- 源码和测试都已更新
- 但本地运行中的 `18080` 还是旧进程
- 导致浏览器看到的 `reports / taxonomy` 仍然回到旧状态或 fallback 口径

后台联调时如果出现“代码看着对，但页面不对”，先确认：

- 当前进程是不是最新代码
- 调到的是不是正确端口
- 前端是不是连到正确环境

## 6.3 后台后续新增接口时保持 requestId 习惯

因为后台已经在 service 层走统一请求封装，后续新增接口建议继续保证：

- 请求带 `X-Request-Id`
- 响应带 `requestId`
- 错误码不要直接裸透第三方或底层异常

这样后续无论本地排查还是上云后的日志排查都更稳。

### 9.5 这对后续后台优先级的影响

因此，后台后续待补点不再是“把 `feed-ops/featured / discussions` 接成真实配置”。

`feed-ops` 这条线当前更适合按“已完成并可验收”处理。后续如果继续做后台增量，优先级应转向：

1. taxonomy 批量修正、筛选治理和更细粒度运营能力。
2. 与社区共享后端的真实数据联动补强。
3. `feed-ops` 的后续增量只围绕真实前台页面继续细化，不再回退到抽象槽位设计。
