# 社区与后台权限边界矩阵

日期：`2026-05-18`

## 目的

这份文档只记录当前代码里已经真实存在的权限边界，避免前台、后台、后端接口对角色理解不一致。

如果文档与代码冲突：

- 以 `apps/server` 与 `apps/web` / `apps/admin` 的当前实现为准
- 再回写这份文档与 `.codex/progress.md`

---

## 当前角色口径

### 社区前台

- `游客`
  - 未持有社区登录态
- `普通登录用户`
  - 已登录社区
  - 当前前台 UI 基本不区分“普通用户”和“创作者”
- `创作者`
  - 当前主要体现在“可发布、可进入个人中心、可进入画布入口”
  - 不是独立后台角色

### 后台管理

- `admin`
  - 系统管理员
- `operator`
  - 运营
- `moderator`
  - 审核员

说明：

- 后台真实角色边界以后端 `AdminAccessService` 为准
- 前台当前没有单独做 `creator` vs `普通登录用户` 的细粒度权限分层

## 后台 API 权限

### 所有后台接口统一前提

- `/api/admin/**` 都必须先通过登录态校验
- 非后台角色即使是普通社区登录用户，也不能使用后台接口

### 模块级角色边界

| 后台接口模块 | `admin` | `operator` | `moderator` | 说明 |
| --- | --- | --- | --- | --- |
| `/api/admin/auth/session` | 可访问 | 可访问 | 可访问 | 后台会话读取 |
| `/api/admin/dashboard/**` | 可访问 | 可访问 | 可访问 | 概览台 |
| `/api/admin/users/**` | 可访问 | 可访问 | 只读可访问 | 用户列表/详情允许三角角色读取；治理变更由服务层限制为 `admin/operator` |
| `/api/admin/comments/**` | 可访问 | 不可访问 | 可访问 | 评论治理 |
| `/api/admin/reports/**` | 可访问 | 不可访问 | 可访问 | 举报中心 |
| `/api/admin/moderation/**` | 可访问 | 不可访问 | 可访问 | 内容审核 |
| `/api/admin/feed-ops/**` | 可访问 | 可访问 | 不可访问 | 运营编排 |

## 当前已确认的产品边界

### 1. 前台的“创作者”不是独立后台权限角色

当前社区前台的 `creator` 更多是业务身份，不是单独的后台鉴权层。

这意味着：

- 能发布内容
- 能管理自己的评论开关
- 能维护自己的资料

但不意味着：

- 可以访问 `/api/admin/**`
- 可以进入后台页面

### 2. 后台权限判断以后端为最终准绳

即使后台前端导航不展示某个页面：

- 也必须由后端再次拒绝非法角色
- 不能把“前端不展示菜单”当成权限边界

### 3. 当前社区前台页面守卫比社区公开 API 更严格

当前实现里：

- 社区部分公开读接口在后端允许匿名调用
- 但前台路由大多仍通过 `proxy.ts` 要求登录后才能进入页面

这是当前产品策略，不是接口能力缺失。

## 第一轮复查结论

本轮已确认：

- 后台前端导航权限与后端服务角色矩阵基本一致
- 社区前台“游客只保留落地页，其他入口跳登录”的策略已在 `proxy.ts` 与页面跳转中落实
- 后续仍建议继续补两类自动化保护：
  - 后台跨角色拒绝访问测试
  - 社区匿名访问受保护写接口测试
