# 测试环境社区前台发布与回滚方案

更新时间：2026-05-19

适用范围：

- 社区前台 `apps/web`
- 社区后端 `apps/server`
- 管理后台前端 `apps/admin` 已自 `2026-05-21` 起单独纳入测试环境云发布，详见 `测试环境管理后台云发布补充-2026-05-21.md`

## 1. 当前真实发布方式

### 1.1 前端

当前通过脚本发布：

- [deploy-test-web.ps1](/E:/点众/DramaTV社区搭建/scripts/deploy-test-web.ps1)

真实流程是：

1. 在本机直接从 `apps/web` 当前工作区打包源码
2. 上传到测试服务器
3. 在服务器 `releases/<timestamp>` 目录里执行：
   - `npm ci`
   - `npm run build`
4. 把 `current` 软链接切到新 release
5. 重启 `dramatv-community-web`

### 1.2 后端

当前通过脚本发布：

- [deploy-test-backend.ps1](/E:/点众/DramaTV社区搭建/scripts/deploy-test-backend.ps1)

真实流程是：

1. 在本机直接从 `apps/server` 当前工作区打包 jar
2. 上传到测试服务器
3. 存放到 `releases/<timestamp>/dramatv-community-server.jar`
4. 把 `current` 指向新的 jar
5. 重启 `dramatv-community-server`

## 2. 当前这套方式的优点

- 已经不是“手工 ssh 上去改文件”了
- 前后端都已经有 `releases/<timestamp>` 目录
- 前后端都已经有 `current` 切换
- 脚本里已经接入：
  - 部署前验证
  - 部署后 readiness 验证

所以它不是完全没有规范，而是：

- 有基础形态
- 但还没有真正进入“可追踪、可审计、可稳定回滚”的阶段

## 3. 当前这套方式的问题

### 3.1 最大问题：发布源来自“本地当前工作区”

当前脚本不是从一个明确的 Git 提交发布，而是从：

- 你电脑上此刻的工作区

直接打包。

这会带来三个风险：

- 容易遗漏：
  - 以为某个改动已同步，其实那次没包含
- 容易重复：
  - 同一个本地改动，可能被多次带进不同云版本
- 难以追溯：
  - 云上某个 release 到底对应本地哪一批代码，事后很难 100% 还原

### 3.2 当前没有正式 release 台账

目前虽然有 release 目录，但缺少稳定的“版本身份证”。

缺少的信息包括：

- 对应 Git commit SHA
- 对应分支
- 是否 dirty workspace
- 发布人
- 发布时间
- 发布说明
- 部署前通过了哪些验证

### 3.3 当前没有正式的一键回滚脚本

虽然结构上可以回滚，但现在还是“手工能力”，不是“流程能力”。

也就是说：

- 能回滚
- 但不够稳
- 也不够方便

### 3.4 数据库回滚能力不完整

后端已有多条 Flyway migration：

- `V10` 到 `V22`

这意味着代码回滚和数据库回滚不是一回事。

当前真实情况是：

- 代码可以切回旧 release
- 但如果新 migration 已经执行，而旧代码不兼容新表结构，就可能回滚失败

所以目前不能说“整个系统已经具备完整回滚能力”。

## 4. 我们现在到底有没有回滚能力

结论分两层。

### 4.1 前后端代码层：有“初级回滚能力”

原因：

- 前端有 `releases/<timestamp>` + `current`
- 后端有 `releases/<timestamp>` + `current`

理论上都可以通过：

- 把 `current` 切回旧 release
- 重启对应 systemd 服务

来恢复之前版本。

### 4.2 整体系统层：还没有“完整回滚能力”

原因：

- 没有稳定 release 台账
- 没有一键 rollback 脚本
- 没有数据库快照 / migration 回退策略
- 以前部分发布来自 dirty workspace，版本边界不清

所以更准确的说法是：

- 现在有“可操作的代码回退手段”
- 但还没有“成熟的测试环境版本管理与回滚体系”

## 5. 为什么现在容易担心遗漏或重复

因为我们当前缺一个关键原则：

- “云环境只能从一个明确版本发布”

现在更像是：

- 本地改一批
- 手工挑着部署
- 再改一批
- 再手工同步一部分

这种方式短期能推进，但一旦修改变多，就会出现：

- 这次到底同步了哪一段
- 那个修复是本地有还是云上有
- 当前云版本到底比本地落后多少

说白了：

- 不是脚本本身完全不行
- 而是“发布对象”没有版本化

## 6. 更成熟的做法

我建议后续把测试环境发布固定成下面这套。

### 6.1 规则一：只从明确 Git 提交发布

不要再默认从“当前脏工作区”直接发。

建议改成：

1. 本地完成一批功能
2. 跑验证
3. 提交到本地 Git
4. 用这个 commit SHA 作为本次发布源

最少也要做到：

- 发布时记录：
  - commit SHA
  - branch
  - dirty=true/false

更理想的是：

- dirty workspace 直接禁止发布

### 6.2 规则二：每次发布都生成 release 元数据

建议前后端每个 release 目录里都落一个 `release.json` 或 `release.txt`，至少记录：

- `releaseId`
- `commitSha`
- `branch`
- `deployedAt`
- `deployedBy`
- `dirtyWorkspace`
- `preVerify`
- `postVerify`
- `notes`

这样以后看到云上的一个 release，不用再靠聊天记忆猜来源。

### 6.3 规则三：单独保留测试环境发布台账

建议新增一份固定台账，例如：

- `ops/releases/test-env-release-ledger.md`

每次发布只追加一条：

- 发了前端还是后端
- release id
- commit SHA
- 主要变更
- 验证结果
- 是否可作为稳定回滚点

### 6.4 规则四：明确“稳定版本”

建议以后每隔一个阶段，标一版“稳定测试版”。

例如：

- `test-stable-2026-05-19-r1`

它不一定是 Git tag，也可以先是本地 release 标签文档，但至少要满足：

- 前后端都已同步
- 核心 smoke 通过
- 页面人工验收通过
- 可以被指定为回滚目标

### 6.5 规则五：数据库改动前必须有回退预案

凡是涉及 migration 的发布，至少要有下面两者之一：

- RDS 快照
- 或显式说明“这次只允许代码前滚，不支持数据库回退”

否则严格意义上不能叫“可回滚发布”。

## 7. 结合我们当前项目，最合适的落地方案

不需要一步到 CI/CD 全自动，先做到下面四点就够了。

### 第一步

先把社区测试环境发布固定成：

- 前端单独批次
- 后端单独批次
- 后台不上云，不混进当前测试环境发布

### 第二步

每次发布前固定做：

- `npm run deploy:verify:pre`

前端额外：

- `npm run typecheck:web`
- `npm run build:web`
- `npm run smoke:web`

后端额外：

- `npm run backend-test:core`
- `npm run backend-test:admin`
- `npm run backend-test:logging`

### 第三步

发布后固定做：

- `npm run readiness:test`

然后补一次人工验收结论。

### 第四步

增加两类脚本：

- `list-releases`
- `rollback-release`

让回滚从“知道能做”变成“有固定入口能做”。

## 8. 对你刚才问题的直接回答

### 8.1 之前我是怎么把本地修改一点点更新到云的

真实方式就是：

- 用当前本地工作区
- 按前端脚本或后端脚本
- 一次次把当前状态打包部署

所以你担心“会不会遗漏或重复”，这个担心是对的。

### 8.2 现在这套方式成熟吗

不算成熟。

更准确地说：

- 已经比纯手工强很多
- 但还没有做到版本化发布

它目前适合：

- 小团队
- 测试环境
- 快速迭代

不适合：

- 长期多人并行且频繁发布
- 强依赖精确追溯和快速回滚

### 8.3 现在有回滚能力吗

有初级代码回滚能力：

- 前后端都能切旧 release 再重启

但没有完整系统回滚能力：

- 缺 release 台账
- 缺一键回滚脚本
- 缺数据库快照策略

### 8.4 能不能定一个稳定版本方便回滚

可以，而且我建议立刻这么做。

最现实的方式是：

1. 先整理出这次准备上云的前端/后端批次
2. 跑完验证
3. 同步到云
4. 人工验收通过后
5. 把这次记成一个稳定测试版

例如：

- `test-stable-2026-05-19-community-r1`

## 9. 下一步建议

当前最合理的下一步不是立刻继续“手工补同步”，而是：

1. 先把“这次要上云的社区前台相关改动”切成明确批次
2. 明确这次是否同时需要带社区后端
3. 发布前做固定验证
4. 同步后把结果登记成第一个稳定测试版

如果继续推进，我建议下一步直接做这三件事：

1. 整理本次社区前台云同步批次
2. 给前后端发布补 release 元数据落盘
3. 增加测试环境 release 台账与 rollback 脚本
