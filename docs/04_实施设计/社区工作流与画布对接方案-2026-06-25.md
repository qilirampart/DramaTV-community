# DramaTV 社区工作流与画布对接方案

> 更新日期：2026-06-25
> 文档目的：对比文件下载式和链接跳转式两种对接方案，为技术决策提供依据

---

## 一、背景

DramaTV 社区需要将工作流从社区侧传递到画布编辑器（独立域名），让用户可以在画布中打开、编辑、运行社区发布的工作流。

**当前约束条件**：
- 社区和画布是独立域名（如 `dramatv.com` 和 `canvas.dramatv.com`）
- 画布侧为独立团队，开发节奏需要协调
- 第一阶段尽量降低技术复杂度和联调成本

---

## 二、方案一：文件下载式

### 2.1 用户操作流程

```
社区工作流详情页 → 点击"下载工作流"
→ 浏览器下载 workflow-xxx.json 文件
→ 用户打开画布网站
→ 画布中点击"导入工作流"
→ 选择刚下载的文件
→ 画布加载并显示
```

### 2.2 社区侧职责

| 职责 | 说明 | 优先级 |
|------|------|--------|
| 下载接口 | `GET /api/workflows/{id}/download`，返回 JSON 文件 | P0 |
| 前端按钮 | 工作流详情页增加"下载工作流"按钮 | P0 |
| 权限检查 | 判断 `workflow.allowCopy` 是否允许下载 | P0 |
| 文件格式 | 构造画布可识别的 JSON 格式（需画布提供规范） | P0 |
| 下载计数 | 统计下载量，用于运营数据（可选） | P2 |

**接口设计**：
```
GET /api/workflows/{id}/download
Response: Content-Type: application/json
         Content-Disposition: attachment; filename="workflow-{id}.json"
Body: {
  "version": "1.0",
  "exportedAt": "2026-06-25T10:30:00Z",
  "sourcePlatform": "DramaTV",
  "workflow": { "id": "...", "title": "...", "author": "..." },
  "definition": { /* 画布定义，格式由画布团队提供 */ }
}
```

### 2.3 画布侧职责

| 职责 | 说明 | 优先级 |
|------|------|--------|
| 导入入口 | 画布界面提供"导入工作流"按钮 + 文件选择器 | P0 |
| 文件解析 | 读取 JSON 文件，校验格式，提取工作流定义 | P0 |
| 画布渲染 | 根据定义渲染节点、连线、参数 | P0 |
| 错误处理 | 格式错误、版本不兼容时的友好提示 | P0 |

### 2.4 优点

- **技术简单**：社区只需提供文件下载，无跨域、鉴权等问题
- **独立开发**：双方几乎不需要联调，各自开发完即可
- **离线友好**：用户可保存工作流文件本地备份
- **无额外依赖**：不需要画布提供 API 接收能力
- **上线快**：预计 1 周可完成社区侧开发

### 2.5 缺点

- **用户体验差**：需要 4 步操作（下载 → 切换网站 → 导入 → 选择文件）
- **无法追踪**：下载后用户是否真正使用、如何修改，社区侧完全不知
- **无法权限控制**：文件一旦下载，社区侧无法再控制使用权限
- **无法建立派生关系**：用户修改后无法溯源到原始工作流
- **移动端体验差**：文件下载+导入在移动端操作繁琐
- **文件管理负担**：用户需要自己管理多个工作流文件
- **无法统计热度**：不能像"复制次数"那样直观反映工作流受欢迎程度

## 三、方案二：链接跳转式

### 3.1 用户操作流程

```
社区工作流详情页 → 点击"在画布中打开"
→ 社区后端记录复制行为，生成 copyId
→ 自动跳转到画布：https://canvas.dramatv.com/launch?copyId=xxx
→ 画布解析参数，调用社区 API 获取工作流定义
→ 画布自动加载并显示
```

### 3.2 社区侧职责

| 职责 | 说明 | 优先级 |
|------|------|--------|
| 复制记录接口 | `POST /api/workflows/copy-to-canvas`，创建复制记录并返回画布跳转 URL | P0 |
| 定义查询接口 | `GET /api/copy-records/{copyId}/definition`，供画布回调获取工作流定义 | P0 |
| 前端按钮 | 工作流详情页增加"在画布中打开"按钮 | P0 |
| 权限检查 | 每次画布请求定义时验证权限（支持付费/私密工作流控制） | P0 |
| 复制记录表 | 新增 `workflow_copy_records` 表，记录复制行为 | P0 |
| 数据统计 | 基于复制记录统计热门工作流、用户行为等 | P1 |

**接口设计**：
```
POST /api/workflows/copy-to-canvas
Request:  { "workflowId": "xxx", "idempotencyKey": "workflow-copy-xxx" }
Response: { "copyId": "xxx", "canvasLaunchUrl": "https://canvas.dramatv.com/launch?copyId=xxx" }

GET /api/copy-records/{copyId}/definition
Response: { "workflow": {...}, "definition": {...} }
```

**数据库新增**：
```sql
CREATE TABLE workflow_copy_records (
  id UUID PRIMARY KEY,
  source_workflow_id UUID NOT NULL,
  operator_id UUID NOT NULL,
  idempotency_key VARCHAR(255),
  status VARCHAR(50) DEFAULT 'created',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(operator_id, source_workflow_id, idempotency_key)
);
```

### 3.3 画布侧职责

| 职责 | 说明 | 优先级 |
|------|------|--------|
| 跳转接收路由 | `/launch?copyId=xxx&source=community`，解析 URL 参数 | P0 |
| 回调社区 API | 用 copyId 调用社区接口获取工作流定义 | P0 |
| 画布渲染 | 根据定义自动加载工作流，无需用户手动导入 | P0 |
| 错误处理 | 网络异常、copyId 无效等情况的降级提示 | P0 |
| 来源标识 | 标记工作流来源为"DramaTV 社区"（可选） | P2 |

### 3.4 优点

- **用户体验好**：一键直达，无需手动下载和导入
- **数据可追踪**：完整记录谁复制了哪个工作流，支持运营分析
- **权限可控制**：每次打开都实时验证权限，支持付费/私密工作流
- **可建立派生关系**：用户修改后可溯源到原始工作流，形成创作链路
- **移动端友好**：无需文件管理，直接跳转
- **可扩展性强**：未来可升级为"在画布中运行""API 远程调用"等高级功能
- **行业主流做法**：Figma Community、Hugging Face 均采用此模式

### 3.5 缺点

- **技术复杂度高**：涉及跨域、鉴权、双方 API 调用
- **画布开发成本大**：画布需开发跳转接收、API 回调、错误处理等能力
- **联调成本高**：双方需紧密配合，预计 2-3 周
- **画布强依赖**：画布 API 不可用时，整个流程中断
- **鉴权问题**：需解决跨域 Cookie / Token 传递
- **需要降级方案**：画布不可用时仍需文件下载兜底

## 四、方案对比总览

| 维度 | 文件下载式 | 链接跳转式 |
|------|----------|----------|
| **用户体验** | ⭐⭐ 4 步操作 | ⭐⭐⭐⭐⭐ 一键直达 |
| **社区开发量** | 1 个接口 + 前端按钮 | 2 个接口 + 1 张表 + 前端按钮 |
| **画布开发量** | 导入功能（必要） | 导入功能 + 跳转路由 + API 回调 |
| **联调成本** | 低，几乎独立 | 高，需频繁配合 |
| **上线周期** | 约 1 周 | 约 2-3 周 |
| **数据追踪** | ❌ 仅能记录下载 | ✅ 完整复制链路 |
| **权限控制** | ❌ 下载后失控 | ✅ 每次实时验证 |
| **派生溯源** | ❌ 无法追溯 | ✅ 可建立家族树 |
| **移动端体验** | ❌ 文件管理繁琐 | ✅ 跳转即可 |
| **离线场景** | ✅ 支持 | ❌ 强依赖网络 |
| **容错性** | ✅ 各自独立 | ⚠️ 相互依赖 |
| **扩展性** | 有限 | 强（可升级运行/API调用） |
| **行业案例** | ComfyUI 官方社区 | Figma、Hugging Face、RunningHub |

## 五、推荐策略：分阶段实施

### 第一阶段（立即）：文件下载式

**选此方案的原因**：
1. 画布团队只需做导入功能（这是画布迟早要有的基础能力）
2. 社区侧完全独立开发，不依赖画布进度
3. 技术风险最低，1 周可上线
4. 先把"工作流从社区到画布"这条链路跑通
5. 后续升级链接式时，文件下载可作为降级方案保留

**第一阶段交付物**：
- 社区：下载接口 + 下载按钮 + 使用指引
- 画布：文件导入功能
- 双方：统一的 JSON 文件格式规范

### 第二阶段：升级链接跳转式

**升级条件**：
- 文件下载式已稳定运行，积累了用户反馈
- 画布团队有开发资源支持跳转接收
- 确认用户需要更流畅的体验
- 运营侧需要复制数据支撑决策

**升级方式**：
- 主按钮改为"在画布中打开"（链接式）
- 保留"下载文件"作为次级选项（降级兜底）
- 画布不可用时自动 fallback 到文件下载

### 长期演进方向

```
文件下载 → 链接跳转 → 画布内直接运行 → API 远程调用
(现在)     (3个月后)    (6个月后)        (未来)
```

## 六、双方需要协商的核心事项

### 6.1 工作流定义格式（最高优先级）

**这是两种方案都需要解决的前提问题**。

| 问题 | 回答方 |
|------|--------|
| 工作流用什么格式存储？ComfyUI 标准？还是自定义？ | 画布团队 |
| 格式规范文档在哪里？ | 画布团队 |
| 能否提供 1-2 个示例 JSON 文件？ | 画布团队 |
| 社区数据库能否直接存储这个格式？ | 社区团队 |
| 是否需要格式转换？ | 双方协商 |

### 6.2 协商步骤

```
第一步：画布团队提供工作流 JSON 格式规范 + 示例文件
第二步：社区团队确认能否存储和原样返回
第三步：确定导出文件的 JSON 结构（外层元信息 + 内层画布定义）
第四步：各自开发
第五步：联调验证（社区导出 → 画布导入）
```

## 七、附录：行业案例参考

| 平台 | 对接方式 | 关键特征 |
|------|---------|---------|
| **Figma Community** | 链接式 | 点击"Open in Figma"直接在设计工具中打开 |
| **Hugging Face Spaces** | 链接式 | "Duplicate this Space"一键复制到个人空间 |
| **GitHub** | 混合式 | Clone（链接式）+ Download ZIP（文件式）并存 |
| **ComfyUI 社区** | 文件式 | 下载 JSON 工作流文件，手动导入 |
| **RunningHub** | 链接式 | 社区工作流可直接在云端 ComfyUI 中打开和运行 |
| **LiblibAI** | 链接式 | 工作流作为资源对象，支持复制到个人空间 |

**结论**：商业化平台普遍采用链接式，但文件式作为基础能力和降级方案，是合理的起点。
