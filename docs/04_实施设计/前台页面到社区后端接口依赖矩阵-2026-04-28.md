# 前台页面到社区后端接口依赖矩阵

更新日期：2026-04-28

## 1. 文档目的

这份文档只做一件事：

- 把当前 `apps/web` 已经真实消费的 `apps/server` 接口逐页拉清楚。
- 同时标记每条链路当前属于 `已可用`、`已接真实后端但待补强`、还是 `演示链路/非 P0`。

规则：

- 以代码现状为准。
- 以前端 `apps/web/src/lib/api/community-service.ts` 和实际路由页为准，不以旧文档口径为准。
- 这份文档用于后续补后端测试、补接口、补状态字段，不是新方案脑暴。

## 2. 当前总判断

当前结论很明确：

- 社区前台已经不是“等后端”的空壳，真实后端接口已经覆盖首页、详情、作者页、讨论区、发布、个人中心、画布演示链路。
- 当前后端主要缺口不是“有没有接口”，而是“读链路测试覆盖不足、发布状态流不够清楚、聚合接口边界不够干净、治理链路还没补齐”。
- 后端下一步应优先补：
  - 读接口集成测试
  - 发布链路状态模型
  - 个人中心与通知聚合
  - 评论/讨论/举报治理闭环
  - `requestId / 错误码 / 日志`

## 3. 状态分级

- `已可用`
  - 前台已直接依赖真实后端，主路径可走通。
- `已接真实后端，待补强`
  - 接口已存在并被前台使用，但测试覆盖、状态表达、性能或治理语义还不够稳。
- `演示链路/非 P0`
  - 当前能跑通演示或占位链路，但不应抢占社区主线排期。

## 5. 上传链路补充说明

当前上传不是直接由浏览器命中 `apps/server` 外域，而是走前端内置代理路由：

- `POST /api/uploads/video-policy`
  - 前端入口：`app/api/uploads/video-policy/route.ts`
  - 代理到后端：`POST /api/uploads/video-policy`
- `POST /api/uploads/image-policy`
  - 前端入口：`app/api/uploads/image-policy/route.ts`
  - 代理到后端：`POST /api/uploads/image-policy`
- `PUT /api/uploads/assets/{assetId}/binary`
  - 前端入口：`app/api/uploads/assets/[assetId]/binary/route.ts`
  - 代理到后端：`PUT /api/uploads/assets/{assetId}/binary`

这意味着后端要重点保证：

- policy 返回的字段稳定
- 二进制上传响应稳定返回 `requestId`
- 失败态能被前端直接展示

## 7. 当前已确认的结构性问题

### 7.1 发布 bootstrap 过度耦合

`getPublishBootstrap()` 当前不是一个后端单接口，而是前端组合了：

- `GET /api/auth/me`
- `POST /api/video-drafts` 或 `GET /api/video-drafts/{id}`
- `POST /api/workflow-drafts` 或 `GET /api/workflow-drafts/{id}`
- `POST /api/post-drafts` 或 `GET /api/post-drafts/{id}`

这意味着：

- 打开 `/publish` 或 `/discussions/new` 时，会一起拉起三类草稿对象。
- 前端对后端草稿模型耦合过深。
- 后端后续很难只针对某一发布场景做独立收口。

建议：

- 后续补一个真正的后端 bootstrap 接口，或至少拆成 `video/workflow/post` 三种更清晰的 bootstrap。

### 7.2 `/me` 聚合仍然重复拉数

`/me` 当前实际是：

- 先读 `GET /api/me/hub`
- 再额外读
  - `GET /api/creators/{id}/videos`
  - `GET /api/creators/{id}/workflows`
  - `GET /api/creators/{id}/posts`

这说明：

- `me` 和 creator 页面边界还没有完全收口。
- 自己主页需要的数据并没有在 `me` 侧完整聚合。

建议：

- 先不推翻现状，但要明确后续是继续让 `me` 走聚合接口，还是补专门的 `me published content` 接口。

### 7.3 canvas 鉴权边界前后端不一致

前端当前要求：

- `/canvas`
- `/canvas/[runtimeId]`

都必须先过 `requireCommunitySession(...)`。

但后端 `SecurityConfig` 当前放开的却包括：

- `GET /api/canvas-runtimes/*`
- `GET /api/canvas-runtimes/*/snapshot`
- `GET /api/canvas-copy-tasks/*`
- `GET /api/workflows/*/canvas-link`

这说明：

- 前后端对 canvas 读接口是否需要登录，当前不是同一口径。

建议：

- 在进入真正 canvas 联动阶段前，先明确是否继续保持“前端要求登录、后端读接口公开”。

## 9. 本文结论

当前前台与后端的真实关系已经比较清楚：

- 读链路已经铺开
- 写链路已经能跑
- 缺的是测试、状态、治理、边界收口

所以下一阶段的后端工作不该再从“新建模块”开始，而应该从：

- 补测试
- 补状态语义
- 补治理闭环
- 补聚合边界

这四件事开始。
