# 社区后端开发规划（结合前台主线）

更新日期：2026-04-28

## 1. 规划前提

- 这次规划不是从零设计后端，而是基于当前真实工程继续推进。
- 当前正式主线固定为 `apps/web + apps/server`，不再回到旧原型。
- 社区前台 `apps/web` 与后台管理 `apps/admin` 在工程上继续分区，但后端统一复用 `apps/server`，不按两套独立后端产品推进。
- 当前产品阶段固定为 `PGC 冷启动阶段`，优先打通社区最小闭环。
- 当前后端主任务不是先做大型管理后台，而是先把前台社区主链路做成真闭环。
- 重媒体处理、AI 任务、工作流 runtime 执行仍然放在 `Python Worker / FastAPI`，`Spring Boot` 负责社区业务编排、状态流转和 API。

## 2. 当前真实现状

### 2.1 前台已经实际消费的页面

- `/home`
- `/videos/[id]`
- `/workflows/[id]`
- `/creators/[id]`
- `/publish`
- `/discussions`
- `/discussions/[slug]`
- `/discussions/new`
- `/me`
- `/prompts/[id]`
- `/canvas/[runtimeId]`
- `/login`

### 2.2 `apps/server` 已有的主要业务模块

- `identity`
- `feed`
- `video`
- `workflow`
- `creator`
- `publish`
- `interaction`
- `canvas`

### 2.3 已有后端能力结论

- 社区公共读接口已经不是空壳，首页、视频、工作流、作者、讨论区、提示词、画布入口都有真实路由。
- 发布链路已经不是纯 mock，草稿、上传、提交、内部回调已经有第一版真实实现。
- 互动链路已经有评论、点赞、收藏、关注的基础能力。
- 后台最小真实闭环已经落了第一步，`/api/admin/auth/**` 和 `/api/admin/users` 已接通。
- `SecurityConfig` 已明确区分公共读接口、登录态接口、后台接口和内部回调接口。
- 集成测试基线已经存在，至少覆盖了 `auth/me`、草稿、评论、互动、发布链路的一部分。

### 2.4 当前最大问题

- 现状不是“有没有后端”，而是“现有后端离前台主线验收还差多少稳定性和治理能力”。
- 现状不是“先做后台页面”，而是“先让前台社区关键链路和后台治理链路都基于真实数据闭环”。

## 3. 后端开发总目标

后端下一阶段只围绕四个目标推进：

1. 把前台社区 `P0` 主链路彻底做成真实闭环。
2. 把发布链路从“能跑”提升到“状态清楚、失败可查、回调可控”。
3. 把互动和治理能力补到足以支撑 `PGC` 社区运营。
4. 把 `requestId / 错误码 / 日志 / 测试` 这套排障基础一并补齐。

## 4. 路线原则

- 以 `apps/web/src/lib/api/community-service.ts` 为前台消费事实，不按抽象未来接口空想。
- 以当前 `apps/server` 实现为基础推进，不做推倒重来。
- 以前台社区与后台管理“前端分区、业务一体化”为固定策略，不把它们当成两套孤立系统分别建模。
- 以 `P0` 社区闭环优先，不让 canvas runtime、推荐系统、复杂搜索抢排期。
- 后台能力服务于社区主链路，不走 admin-first 的倒排路线。
- 同类字段命名、状态命名、错误码命名统一收口，不允许前后端各说各话。

## 5. 分阶段开发规划

## 5.1 Phase 0：前后端契约收口

目标：把“当前页面依赖什么接口、哪些字段已真实、哪些还是占位”一次性说清楚。

工作项：

- 逐页整理 `apps/web` 对 `apps/server` 的接口依赖矩阵。
- 对齐 `docs/04_实施设计/第一阶段 API 清单.md`、`docs/04_实施设计/Next.js 页面数据契约.md` 和代码现状。
- 标记每个交互是 `前端占位 / 已接后端但未联调完成 / 已可用`。
- 收口状态字段命名，例如 `draftStatus`、`moderationStatus`、`processingStatus`、`visibility` 的边界。
- 拉出一份缺口清单，避免开发过程中反复补洞。

完成标准：

- 前台每个核心页面都能明确对应接口、字段和状态来源。
- 文档和代码的差异被记录清楚。
- 后续开发不再出现“前端以为有、后端其实没有”的口径分裂。

## 5.2 Phase 1：P0 读链路稳定化

目标：优先稳住前台社区的读路径。

覆盖范围：

- 首页 `feed`
- 视频详情
- 工作流详情
- 作者主页
- 个人中心
- 讨论区首页与详情
- 提示词详情

工作项：

- 补齐读接口的空字段、缺失字段和弱约束字段。
- 统一资源 URL 解析、封面/preview/source 回退策略。
- 收口公共读接口的空值处理、排序规则、分页规则和兜底逻辑。
- 增加 `feed / video / workflow / creator / me / discussion / prompt` 的 HTTP 级集成测试。
- 检查查询热点，补必要索引和查询约束。

完成标准：

- `apps/web` 的核心读页面不再依赖运行时 mock 兜底。
- 公共读接口返回结构稳定，前台页面不需要为同类数据写多套兼容逻辑。
- P0 页面至少具备本地联调可用的真实读链路。

## 5.3 Phase 2：发布链路完成度提升

目标：把 `/publish` 从“草稿能保存”推进到“可发布、可审核、可追踪”。

覆盖范围：

- `video-drafts`
- `workflow-drafts`
- `post-drafts`
- `uploads`
- `internal callbacks`
- `moderation`

工作项：

- 完成发布 bootstrap、上传策略、二进制上传、草稿保存、提交审核、审核回调、内容入库的完整状态流。
- 明确区分 `草稿状态`、`审核状态`、`媒体处理状态`、`发布可见性`。
- 增加异步任务状态查询和失败原因返回，不能只靠猜。
- 补回调幂等、防重和失败重试策略。
- 确保视频与工作流绑定关系在发布后可直接回流到视频详情页和工作流详情页。

完成标准：

- 创作者能通过真实后端完成一次最小发布闭环。
- 运营或审核能看见待审核内容并完成状态流转。
- 前台能感知“处理中 / 待审核 / 已发布 / 被驳回”等真实状态。

## 5.4 Phase 3：互动与社区闭环补强

目标：把“看内容”推进到“能互动、能沉淀关系、能治理”。

覆盖范围：

- 评论
- 点赞
- 收藏
- 关注
- 举报
- 讨论区发帖
- 个人资料与消息

工作项：

- 补齐评论目标开关、删除、隐藏、举报联动。
- 补齐讨论帖发布链路和讨论详情页依赖字段。
- 收口点赞、收藏、关注的幂等行为和返回结构。
- 补齐 `/api/reports` 的工单语义和后续治理挂钩。
- 把 `/api/me/profile`、`/api/me/notifications/recent` 做到前台可真实依赖。

完成标准：

- 用户可以在真实后端上完成互动动作，不再只是前端状态切换。
- 举报和评论治理能进入后台处理，而不是只留前台入口。
- 个人中心和讨论区不再长期处于“半真半假”状态。

## 5.5 Phase 4：后台治理能力建设

目标：后台只建设当前社区主线真正需要的治理能力。

优先级顺序：

1. `admin auth / session`
2. `users`
3. `moderation`
4. `reports`
5. `comments`
6. `feed ops`
7. `audit logs`

工作项：

- 在 `apps/server` 下继续扩展 `/api/admin/**`。
- 先完成审核队列、举报工单、评论治理、用户状态管理。
- 再补首页/精选/讨论区的运营排序与人工配置。
- 所有后台操作都记审计日志，保留操作者、时间、对象、动作和结果。

完成标准：

- 后台能承接前台发布和互动链路带来的治理需求。
- 管理后台不再只是“能登录”，而是能处理最核心的运营动作。
- 后台范围仍然严格停在社区治理，不扩到 canvas runtime 管理。

## 5.6 Phase 5：可观测性、错误码和交付加固

目标：把排障成本降下来，避免功能做出来但问题查不动。

工作项：

- 全链路补 `X-Request-Id` 生成、透传、响应回写和日志落地。
- 关键业务日志补 `userId / videoId / workflowId / draftId / commentId / moderationTaskId / copyTaskId`。
- 建立统一错误码映射，不把第三方原始错误直接丢给前端。
- 拆分访问日志、应用日志、错误日志，并保证滚动切分。
- 增加本地 smoke 脚本和后端集成测试覆盖。
- 补部署检查项：数据库迁移、对象存储配置、Redis、回调密钥、任务开关。

完成标准：

- 关键失败场景都能基于 `requestId` 和业务 ID 快速定位。
- 前端拿到的是“可显示文案 + 错误码 + requestId”。
- 后端具备基本可上线排障能力，而不是只能看控制台。

## 6. 推荐实施顺序

建议按下面顺序推进，而不是并行散打：

1. 先做 Phase 0，冻结契约和缺口清单。
2. 再做 Phase 1，把核心读链路稳定住。
3. 然后做 Phase 2，完成发布和审核状态闭环。
4. 接着做 Phase 3，把互动和举报链路补齐。
5. 再做 Phase 4，让后台具备治理能力。
6. Phase 5 从现在就开始同步补，但最晚要在上线前完成基础闭环。

## 7. 近期首批任务清单

建议后端接下来先落这 10 项：

1. 输出一份 `apps/web -> apps/server` 的页面接口依赖矩阵。
2. 给 `feed / video / workflow / creator / me / discussion / prompt` 补齐集成测试。
3. 逐页核对前台 P0 页面是否还存在关键 mock 兜底。
4. 收口发布草稿、审核、媒体处理三套状态字段。
5. 增加发布异步任务状态查询和失败原因返回。
6. 完成内部回调的幂等、防重和异常日志补齐。
7. 补齐举报工单和评论治理的真实后台接口。
8. 把 `/api/me/profile`、`/api/me/notifications/recent` 补到前台可正式依赖。
9. 扩展后台到 `moderation / reports / comments` 三个核心页面对应接口。
10. 补 `TraceIdFilter`、统一错误码和日志落地策略。

## 8. 明确暂不优先做的内容

这轮后端规划明确不把下面这些放到主线前面：

- 新拆一套社区后端微服务
- 真实 canvas runtime 管理后台
- 复杂推荐系统
- 全站高级搜索
- 大型通知中心
- 复杂运营活动系统
- 直接从后台前端绕过 API 写数据库

## 9. 规划结论

后端下一阶段不该被理解成“从零开始搭 Java 服务”，而应该被理解成：

- 基于现有 `apps/server` 把前台社区真实消费的接口做稳。
- 基于现有发布与互动能力把 `P0` 闭环补成完整产品链路。
- 基于现有 `/api/admin/**` 起点补最小治理后台。
- 同步把测试、日志、错误码、`requestId` 这套工程基础打牢。

一句话收口：

`先把前台社区主线背后的真实后端闭环做完整，再把后台治理能力接上来。`
