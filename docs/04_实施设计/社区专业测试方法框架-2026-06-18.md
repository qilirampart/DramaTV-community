## 1. 这套方法到底在做什么

这套“专业测试”方法的重点不是多写一点用例，也不是机械把页面点一遍，而是先回答 4 个问题：

1. 这轮到底测什么，不测什么。
2. 哪些地方风险最高，应该先花时间。
3. 每个问题要测到多深，铺到多广。
4. 测完以后，结果怎么沉淀成下轮还能继续复用的资产。

对 DramaTV 社区项目来说，它的价值不是“理论更完整”，而是避免后面继续出现这类低效情况：

- 只测首屏，不测深滚动和多跳返回。
- 只看页面能打开，不看数据语义是不是错了。
- 只修当前 bug，不把同源风险页面一起扫掉。
- 只在聊天里说问题，没有沉到任务板和回归口径。

## 2. 测试思路

### 2.1 先规划，再下钻

顺序固定为：

1. 先做范围规划。
2. 再做风险排序。
3. 再按维度拆测试点。
4. 最后才写执行用例和回归链路。

这意味着测试不是从“我先点点看”开始，而是从“这轮最高风险在哪里”开始。

### 2.2 先测风险，不平均用力

在社区项目里，高风险不等于页面多，而是满足下面任一条件：

- 最近改动频繁。
- 真机数据量大。
- 状态切换复杂。
- 牵涉共享逻辑。
- 一旦错了，用户体感很差。

按这个标准，当前高风险排序应长期优先看：

1. `/featured`
2. `/creators/[id]`
3. `/discussions`
4. `/login` 与会话链路
5. `/home`
6. `/me`
7. `/publish`
8. 详情页族：`/prompts/[id]`、`/videos/[id]`、`/workflows/[id]`

### 2.3 用“链路”替代“单页”

社区项目不能按单页割裂测试，应该按真实链路测。

典型链路：

- `featured -> detail -> creator -> creator work detail -> back -> back`
- `discussions -> post detail -> creator -> back`
- `home -> detail -> back`
- `featured deep scroll -> detail -> back -> continue load`
- `unauth route -> login -> redirect back`

判断标准不是“某一页打开了”，而是整条链路里状态、定位、分类、登录态、分页都没丢。

## 3. 测试维度

这套方法的“维度”可以直接翻译成 DramaTV 社区的固定检查轴。

### 3.1 功能维度

看功能能不能用。

适用点：

- 登录
- 首页浏览
- 精选切分类
- 帖子打开
- 作者页查看更多
- 发布页进入

### 3.2 状态维度

看页面状态切换是否正确。

重点检查：

- 加载中
- 空态
- 错误态
- 返回定位中
- 已登录 / 未登录
- 首屏 / 非首屏
- 已预取 / 未预取

### 3.3 数据语义维度

看“展示对不对”，不只是“有没有内容”。

重点检查：

- 精选页是否混入帖子。
- 活动分类下是否错误出现帖子。
- 图片提示词 / 视频提示词分类是否正确。
- 作者页作品数量是否和真实发布一致。
- 标题、简介、封面策略是否符合当前产品口径。

### 3.4 交互维度

看用户操作连续发生时会不会乱。

重点检查：

- 快速切换分类
- 快速多次返回
- 深滚动后再点详情
- 切主题后再继续滚动
- 详情页返回后继续加载

### 3.5 边界维度

看极端条件是否还成立。

对当前社区最关键的边界是：

- 首批 12 条以内
- 100 条以上深滚动
- 300 条级别深滚动
- 首次返回
- 多跳返回
- 第一批分页和后续分页的衔接

### 3.6 会话与权限维度

看登录态和权限边界。

重点检查：

- 未登录访问受保护页
- 登录后是否回到原路由
- 已登录访问 `/login` 是否正常跳出
- 深链路浏览时是否意外掉登录

### 3.7 性能与体感维度

看“能用”之外，体感是否明显差。

重点检查：

- 首屏是否慢
- 分类切换是否卡
- 返回定位是否等太久
- 瀑布流加载是否抖动
- 深滚动后是否卡死

### 3.8 可观测性维度

看出了问题能不能定位。

重点检查：

- 控制台是否有高频错误
- 接口失败时是否有稳定报错
- 是否能关联到具体路由和操作链

## 4. 深度和广度

这是这套方法最容易说空的一部分，这里直接按项目解释。

### 4.1 什么叫广度

广度是把同类问题铺开到相关页面。

例如“返回定位”这个问题，广度不是只测 `/featured`，而是一起看：

- `/featured`
- `/discussions`
- `/creators/[id]`
- `/me`
- 详情页返回上层列表

广度解决的是“是不是还有漏网之鱼”。

### 4.2 什么叫深度

深度是在一条高风险链路里不断往下压，直到共享状态、分页、缓存、定位、路由都经受住。

例如 `/featured` 的深度测试不是打开一下列表，而是：

1. 滚到 100 条以上。
2. 打开详情。
3. 进入作者页。
4. 在作者页继续查看更多。
5. 再进作者作品详情。
6. 连续返回。
7. 回到精选后继续滚动。
8. 再切换分类。

深度解决的是“当前看着没问题，复杂操作会不会塌”。

### 4.3 当前项目该怎么平衡

对 DramaTV 社区当前阶段，建议：

- 先用广度扫主链路是否全通。
- 再把时间主要砸在 `/featured`、`/creators/[id]`、`/discussions` 的深度测试上。

不要平均分配时间。

## 5. 对应到社区项目的执行框架

### 5.1 L1 主路径冒烟

目标：确认主入口没挂。

覆盖：

- `/login`
- `/home`
- `/featured`
- `/discussions`
- `/publish`
- `/me`

### 5.2 L2 高风险链路

目标：确认最容易出体感故障的链路稳定。

覆盖：

- 精选深滚动与自动加载
- 精选分类快速切换
- 精选多跳返回
- 讨论区帖子详情返回
- 作者页查看更多与返回
- 登录态守卫与 redirect 回路

### 5.3 L3 数据语义与内容正确性

目标：确认真实数据没有把前台展示带偏。

覆盖：

- 分类混排
- 帖子误入精选
- 作者页作品数量偏差
- 标题/简介/封面展示口径
- 搜索结果与分类语义一致性

### 5.4 L4 稳定性与体感

目标：确认没有“功能正常但用户感觉很差”的问题。

覆盖：

- restoring 卡死
- 返回后不再加载
- 瀑布流重排明显抖动
- 深滚动后卡死
- 云端大数据量下的切换延迟

## 6. 这套框架在 DramaTV 社区里的固定优先级

每轮测试优先级建议固定如下：

1. 会话与登录链路
2. `/featured` 高风险链路
3. `/creators/[id]` 与 `/me` 返回链路
4. `/discussions` 列表与详情返回
5. 数据语义与搜索质量
6. 视觉与主题可读性
7. 本地 smoke / backend integration 回归

原因很简单：

- 前 4 类最影响真实用户体感。
- 第 5 类最容易造成“页面能打开，但内容不可信”。
- 第 6 类会直接影响可读性和演示质量。
- 第 7 类是工程兜底，但不能替代浏览器真实链路。

## 7. 你们这个项目该怎么落到日常工作

### 7.1 开发前

先写清楚这轮改动影响哪些链路，不要只写影响哪个页面。

### 7.2 开发后

至少补 3 件事：

1. 主路径冒烟。
2. 相邻页面广度扫一遍。
3. 最高风险链路做一次深测。

### 7.3 上云前

必须检查：

- 是否有共享逻辑被改到
- 是否涉及返回定位
- 是否涉及分页 / 瀑布流 / 分类切换
- 是否涉及登录态与 redirect
- 是否涉及真实云端脏数据

### 7.4 上云后

不要只看“页面打开正常”，至少补：

- 新标签页干净验证
- 深滚动验证
- 多跳返回验证
- 控制台错误抽查

## 8. 当前项目的长期固定高风险区

后面每轮测试都应该默认重点盯这几类：

1. `/featured` 的深滚动、分类切换、返回定位、继续加载。
2. `/creators/[id]` 的分页保态、首次返回、深层详情往返。
3. `/discussions` 的帖子详情返回、频道切换、发布入口守卫。
4. `/login` 的已登录/未登录边界与 redirect 语义。
5. 真实云端数据下的分类、搜索、混排正确性。

## 9. 当前结论

这套“专业测试”方法放到 DramaTV 社区里，实质上就是一句话：

先按风险挑链路，再用维度拆问题，然后用广度防漏、用深度防假正常，最后把结果沉到任务板和回归口径里。

对当前项目来说，这比“页面逐个点一下”更合适，因为你们现在真正难的不是单页可用，而是：

- 深链路状态保持
- 真实数据语义正确
- 云端大数据量下的稳定性
- 改一个点不把其他链路带坏
