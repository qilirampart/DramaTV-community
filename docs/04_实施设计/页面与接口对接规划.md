# DramaTV 页面与接口对接规划

更新日期：2026-04-07

## 1. 文档目标

这份文档用来把 DramaTV 当前正式前端的页面分成两层：

- 第一层：资源对象层
- 第二层：独立讨论层

核心目的不是继续发散页面想法，而是把下面三件事一次说清楚：

1. 哪些页面已经走真实后端
2. 哪些页面当前只是前端骨架
3. 后续讨论系统要补哪些接口，才不会把已经打通的资源主线打散

## 3. 两层页面边界

### 3.1 第一层：资源对象层

当前已经走真实后端的，是围绕具体对象展开的页面：

- 首页
- 视频详情页
- 工作流详情页
- 作者主页
- 发布页
- 画布运行态页

这些页面的共同特点是：

- 都围绕明确对象展开
- 已经有稳定的接口主线
- 可以继续向后补真实业务能力

### 3.2 第二层：独立讨论层

当前新补的讨论区页面，不承接“某个视频对象的即时反馈”，而承接横向经验：

- 提示词拆解
- AI 视频制作经验
- 画布工作流分享经验

这层页面的定位是：

- 沉淀经验
- 做帖子结构
- 做经验帖与资源对象的桥接

不应该做成：

- 把对象评论重新复制一遍
- 抢走工作流详情页的复制入口
- 把首页主 feed 变成纯论坛流

- `GET /api/creators/{id}/workflows`

### 4.2 对象评论与基础互动

- `POST /api/interactions/favorite`

## 5. 讨论层当前只做前端骨架

当前 `/discussions` 与 `/discussions/[slug]` 不再使用本地静态 view model 伪装真实帖子。

当前统一按下面方式表达状态：

- 资源对象层：继续走真实后端
- 独立讨论层：明确标记“后端待接入”，不再展示假数据

这样可以避免把“未来要做的论坛系统”误认为“当前已经完成的真实能力”。

## 6. 讨论层建议的数据实体

为了避免后续帖子系统和对象评论混淆，建议讨论层单独建实体：

```ts
type DiscussionChannel = {
  id: string
  slug: string
  title: string
  summary?: string
  sortOrder: number
}

type DiscussionThread = {
  id: string
  slug: string
  channelId: string
  authorId: string
  title: string
  summary?: string
  contentMarkdown: string
  status: 'published' | 'hidden' | 'locked'
  createdAt: string
  updatedAt: string
}

type DiscussionReply = {
  id: string
  threadId: string
  parentReplyId?: string
  authorId: string
  content: string
  createdAt: string
}

type DiscussionBinding = {
  id: string
  threadId: string
  targetType: 'video' | 'workflow'
  targetId: string
}
```

关键点：

- 对象评论继续用现有 `Comment`
- 独立讨论帖不要复用 `Comment` 直接充当主楼
- 帖子和资源对象的关系单独通过 `DiscussionBinding` 表达

## 7. 讨论层建议补的接口

建议下一阶段从最小闭环开始：

### 7.1 读接口

- `GET /api/discussions/home`
- `GET /api/discussions/threads/{slug}`
- `GET /api/discussions/channels/{slug}/threads`

### 7.2 写接口

- `POST /api/discussions/threads`
- `POST /api/discussions/replies`
- `POST /api/discussions/replies/{id}/like`
- `DELETE /api/discussions/replies/{id}/like`

### 7.3 绑定接口

- `POST /api/discussions/threads/{id}/bindings`
- `DELETE /api/discussions/threads/{id}/bindings/{bindingId}`

## 8. 推荐推进顺序

1. 继续保持资源对象层全部走真实后端，不回退到 mock 验收；当前仓库也不再保留前后端运行时 mock 分支。
2. 先把讨论区首页和帖子详情页骨架固定住，让产品边界先清楚。
3. 再补讨论层最小实体和最小读写接口。
4. 最后再补帖子排序、精选、搜索、分区订阅和运营位。

## 9. 当前结论

当前最稳妥的推进方式已经明确：

- 资源对象层继续走真实后端主线
- 独立讨论层先用前端骨架钉住结构
- 对象评论和独立讨论分层，不混为一个系统

这样后面无论继续补后端、做界面重构，还是和别人解释项目结构，都不会跑偏。
