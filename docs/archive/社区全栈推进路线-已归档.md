# DramaTV 社区全栈推进路线

更新日期：2026-04-06

## 1. 这次要解决的不是“页面开发”，而是“社区全栈落地顺序”

当前项目已经不能再按“先做几个前端页面，后面再补后端”来推进。

DramaTV 现在要做的是：

- 一个 AI 视频生成社区
- 一个方法交流社区
- 一个工作流发布与复用社区
- 一个与画布软件联动的创作入口

因此后续规划必须同时覆盖：

- 前端页面与交互链路
- 后端服务边界
- 数据模型
- 内容发布与审核
- 基础安全
- 文件与媒体处理
- 基本负载均衡与扩展能力

结论：

- 这是一个“社区产品 + 内容平台 + 工具联动”的全栈项目
- 不能只用前端项目规则来约束
- 但也不能一上来就进入技术实现，必须先把流程和架构搞清楚

## 2. 推荐推进顺序

建议接下来严格按下面顺序推进：

1. 补齐参考社区研究
2. 明确业务流程与系统边界
3. 画出全栈架构与核心服务关系
4. 再分析并确定技术栈
5. 最后重写项目规则文档
6. 再进入分阶段开发

这个顺序的原因很简单：

- 没有参考对象，容易把社区做偏
- 没有流程和边界，技术栈会选错
- 没有服务拆分和安全边界，规则文档会失真
- 没有规则约束，后面实现会再次失控

## 4. 第一步：补齐参考社区研究

这一阶段的目标不是“多收集素材”，而是回答 4 个问题：

### 4.1 这些社区是怎么定义内容对象的

我们重点要看：

- 视频作品是不是一级对象
- 工作流是不是一级对象
- 作者主页是不是强入口
- 评论是围绕对象还是围绕 feed
- 是否支持提示词、参数、工作流、模型等“方法信息”的公开展示

### 4.2 这些社区的发布链路怎么设计

重点看：

- 发布作品需要哪些字段
- 发布工作流需要哪些字段
- 是否区分草稿、公开、私有、仅链接可见
- 是否有审核、精选、推荐机制

### 4.3 这些社区怎么处理“工具与社区”的关系

重点看：

- 工具是独立站还是社区内入口
- 社区内容能否直接带回工具继续编辑
- 工作流是否可复制、派生、Fork

### 4.4 这些社区的治理方式是什么

重点看：

- 是否有内容审核
- 是否有精选机制
- 是否有榜单、活动、扶持
- 是否把“优质创作者”作为一条运营主线

这一阶段的交付建议是：

- 重写或升级现有竞品研究文档
- 把 `Liblib / RunningHub / TapTap / Figma / Midjourney / Hugging Face / Krea / Runway` 纳入一个统一对照表
- 明确“可借鉴”“不可照搬”“对技术架构的影响”

## 5. 第二步：先定业务流程，再定系统架构

技术架构不应脱离业务流程。

建议先画清楚 5 条核心业务流：

### 5.1 游客浏览流

- 进入首页
- 浏览作品
- 浏览工作流
- 查看作者
- 进入详情页

### 5.2 创作者发布流

- 登录
- 上传视频
- 填写标题、简介、标签、分区
- 绑定工作流
- 选择可见性
- 提交审核或直接发布

### 5.3 工作流发布流

- 上传工作流封面和说明
- 补充适用场景、标签、参数说明
- 选择是否允许复制 / 派生
- 生成详情页
- 支持后续在画布中打开

### 5.4 社区互动流

- 评论
- 点赞
- 收藏
- 关注
- 举报

### 5.5 运营治理流

- 审核内容
- 精选推荐
- 设置活动
- 下线违规内容
- 处理举报

只有把这 5 条链路画清楚，后面才能判断：

- 哪些是同步请求
- 哪些必须异步处理
- 哪些要拆成独立服务
- 哪些要引入审核和风控

## 6. 第三步：全栈架构先定边界，不急着定实现语言

在技术栈选择前，建议先把系统边界定成下面这几层：

### 6.1 接入层

- Web 前端
- 后续移动端或 H5
- 画布软件入口 / 插件入口
- 管理后台

### 6.2 网关与流量层

- CDN
- 负载均衡
- 反向代理
- API 网关

### 6.3 应用服务层

- 用户与鉴权服务
- 内容服务
- 工作流服务
- 评论与互动服务
- 发布与审核服务
- 推荐与运营服务
- 画布联动服务

### 6.4 异步任务层

- 视频转码
- 封面提取
- 预览视频生成
- 内容审核任务
- 通知任务
- 搜索索引更新

### 6.5 数据与基础设施层

- 关系型数据库
- 对象存储
- 缓存
- 搜索引擎
- 消息队列
- 日志与监控

这里先回答“有哪些服务”，不要马上回答“每个服务用什么语言写”。

## 7. 第四步：安全和负载均衡要从架构阶段一起考虑

这两个问题不能等到开发后期才想。

### 7.1 最基础的安全要求

第一阶段至少要覆盖：

- 登录鉴权
- 角色权限控制
- 文件上传校验
- 评论和发布接口限流
- XSS / CSRF / SQL 注入基础防护
- 敏感操作审计日志
- 对象存储访问控制
- 内容审核与举报入口

建议把安全拆成 4 类：

- 账号安全
- 内容安全
- 接口安全
- 媒体资源安全

### 7.2 最基础的负载均衡要求

第一阶段不需要追求复杂分布式，但要预留扩展方式：

- 静态资源走 CDN
- 应用服务放在负载均衡后面
- 视频与图片走对象存储，不放应用机本地
- 转码、预览生成、审核走异步任务
- 热门内容和首页数据要有缓存
- 搜索与主库分开考虑，不要把模糊搜索压在主库上

结论：

- 安全和负载均衡不是“上线前补一下”
- 它们会直接影响你们的架构拆分和技术栈选择

## 8. 第五步：技术栈分析应该怎么做

技术栈选择不要按“团队谁最熟”直接拍板。

应该先按下面 6 个问题评估：

### 8.1 前端形态

- 是纯 SPA，还是 SSR / SSG / 混合渲染
- 首页、详情页、作者页是否需要更强 SEO
- 发布中心和后台是否适合做成同一套前端

### 8.2 后端形态

- 是单体优先，还是拆微服务
- 第一阶段是否采用模块化单体更合适
- 鉴权、内容、评论、审核、工作流联动是否先在同一后端中分模块

### 8.3 数据层需求

- 是否以关系型数据为主
- 是否需要搜索引擎支持作品、工作流、作者检索
- 是否需要缓存层承接热门内容

### 8.4 媒体处理需求

- 是否要接视频转码
- 是否要生成多尺寸封面、预览
- 是否需要异步任务编排

### 8.5 团队与运维约束

- 团队更擅长 Node、Java、Go 还是 Python
- 是否有现成云资源和 DevOps 体系
- 是否需要快速交付第一版还是追求更强后续扩展

### 8.6 画布联动方式

- 是通过 HTTP API 联动
- 还是通过插件 / SDK 联动
- 是否需要 OAuth、签名、回调机制

技术栈选择阶段的交付建议是：

- 输出一个“候选技术栈对照表”
- 不少于 2 套候选方案
- 每套方案写清楚优点、风险、适用阶段、后续扩展性

新的规则文档至少要覆盖：

### 9.1 项目定位

- 不只是视频 feed

### 9.2 范围分层

- 后端范围
- 运营与审核范围
- 画布联动范围

### 9.3 数据模型与服务边界

- 核心实体
- 核心服务
- 媒体资源模型
- 可见性与权限模型

### 9.4 安全规则

- 上传限制
- 鉴权方式
- 接口限流
- 日志与审计
- 内容审核边界

### 9.5 性能与扩展规则

- CDN
- 缓存

- 异步任务

### 9.6 开发流程规则
