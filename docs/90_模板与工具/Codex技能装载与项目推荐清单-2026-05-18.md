## 4. 项目内推荐基线

### 4.1 默认基线

日常编码默认先带一层：

- `karpathy-guidelines`

原因：

- 它最适合做底层行为护栏
- 可以持续约束本项目里最常见的问题：过度设计、顺手改无关代码、没有验收标准就开工

### 4.2 叠加原则

不要一次堆太多 skill。推荐按下面的组合方式使用：

1. `1` 个基线 skill：通常是 `karpathy-guidelines`
2. `1` 个场景 skill：按当前任务类型选择
3. `1` 个验证 skill：用于测试、review、debug 或上线检查

如果任务很小，只用基线 skill 即可。

## 5. DramaTV 项目推荐搭配

### 5.1 前端页面开发与精修

优先使用：

- `frontend-ui-engineering`
- `browser-testing-with-devtools`
- `performance-optimization`

适用任务：

- `apps/web`、`apps/admin` 页面实现
- 后台和社区页的布局、交互、弹窗、筛选、分页
- 浏览器运行态验收
- 视频卡片、首屏媒体、列表性能排查

### 5.2 后端接口、契约与领域收口

优先使用：

- `source-driven-development`
- `api-and-interface-design`
- `spec-driven-development`
- `security-and-hardening`

适用任务：

- `apps/server` 的 controller、service、query、DTO、integration test
- API 契约收口
- 请求/响应字段命名统一
- 鉴权、审核、错误码、日志边界补强

### 5.3 调试、回归与问题定位

优先使用：

- `debugging-and-error-recovery`
- `code-review-and-quality`
- `test-case-generation`

适用任务：

- 线上或本地真实问题复现
- 前后端联调异常
- 接口 `500`、登录态异常、页面转圈、发布链路失败
- 回归测试补点和测试清单设计

### 5.4 大任务拆解与持续推进

优先使用：

- `planning-and-task-breakdown`
- `incremental-implementation`
- `context-engineering`
- `doubt-driven-development`

适用任务：

- 后台治理模块分阶段开发
- 社区主线和后台线并行推进
- 复杂功能的拆步落地
- 长会话下的上下文整理和约束收口

### 5.5 重构、清理与迁移

优先使用：

- `code-simplification`
- `deprecation-and-migration`
- `git-workflow-and-versioning`

适用任务：

- 去掉旧占位逻辑
- 清理双路径实现

- shared layer 收口

### 5.6 文档、方案和发布准备

## 7. 使用约束

后续使用这批 skills 时，保持下面几条规则：

- skill 只增强执行方式，不替代项目规则
- 业务优先级仍以 `P0 / P1 / P2` 和当前真实代码状态为准
- 不因为 skill 存在就人为制造复杂流程
- 能直接做小补丁解决的问题，不先拉一整套 spec 流程
- 新增 skill 使用经验，如果在本项目内被反复验证有效，再补进 `memory/MEMORY.md`

## 8. 后续维护规则

- 新增第三方 skill 时，先判断是否和现有 skill 重名或职责重叠
- 默认继续沿用“只补缺，不覆盖”的安装策略
- 如果未来决定升级某个同名 skill，要单独记录升级来源、覆盖范围和理由
- 如果 Codex 全局 skills 再次变动，应同步更新本文件
