# 前端社区项目轻量规则模板

适用场景：视频社区、内容社区、创作者社区、作品发布平台、社区型前端项目。  
目标：用尽量少的规则，保证项目可继续、可协作、可回溯，同时覆盖社区产品最容易失控的几个关键点：页面范围、数据模型、组件体系、媒体资源和交互边界。

## 1. 核心原则

- 规则必须可执行，不写空话。
- 默认保持轻量，只有在复杂度上升时才补充机制。
- 优先记录关键决策、当前状态、下一步，不追求面面俱到。
- 所有过程文档以“帮助下一次继续工作”为目标。

## 2. 最小文件结构

建议只保留 3 个核心文件：

```text
项目根目录/
├─ CLAUDE.md
├─ .codex/
│  └─ progress.md
└─ memory/
   └─ MEMORY.md
```

说明：

- `CLAUDE.md`
  - 项目规则主文件，写清范围、限制、目录约定、交付标准。
- `.codex/progress.md`
  - 当前项目进度文件，记录阶段、待办、最新决定。
- `memory/MEMORY.md`
  - 沉淀稳定经验，避免重复踩坑。

以下内容默认不强制：

- `genes/`
- `capsules`
- 多层归档规则系统

只有在项目进入多人协作、长期演进、经验复用频繁时再加。

## 3. 会话恢复规则

每次新会话开始时，按顺序读取：

1. `CLAUDE.md`
2. `.codex/progress.md`
3. `memory/MEMORY.md` 中与当前任务直接相关的部分

恢复目标：

- 先知道项目当前目标
- 再知道现在做到哪里
- 最后知道有哪些已经验证过的经验不要重复试

如果 `progress.md` 与实际代码不一致，以代码现状为准，并补记差异。

## 4. 进度文件规则

`.codex/progress.md` 建议固定为 3 段：

### 4.1 当前快照

只保留最新状态，内容不超过 10 行：

- 当前阶段
- 当前主目标
- 当前风险
- 当前产出物

### 4.2 当前看板

只保留少量任务：

- `Todo`
- `Doing`
- `Done`

每项任务用一句话写清楚，不拆过细。

### 4.3 追加日志

采用 append-only，只追加，不覆盖历史：

- 日期
- 做了什么
- 结果如何
- 下一步是什么

日志只记关键动作，不写流水账。

## 5. 状态机

轻量项目统一使用 5 个状态：

- `Idea`
  - 需求和方向还在确认
- `Plan`
  - 已明确页面结构、范围、技术方案
- `Build`
  - 正在实现页面、交互、数据接入
- `Review`
  - 正在验收、修正、整理交付
- `Done`
  - 当前范围已完成，可以交付或归档

状态切换规则：

- 没有明确范围，不进入 `Build`
- 没有验证，不进入 `Done`
- 一旦发现主目标变化，退回 `Plan`

## 6. 写入时机

只在以下时机更新文档：

- 新项目初始化时
- 任务方向发生变化时
- 完成一个阶段性里程碑时
- 遇到明确坑点并确认解决方案时
- 交付前整理时

推荐写入顺序：

1. 先更新 `progress.md`
2. 再补充 `MEMORY.md`
3. 最后在必要时调整 `CLAUDE.md`

原因：

- 进度变化最频繁
- 经验沉淀次之
- 总规则最稳定，不应高频修改

## 7. 页面范围规则

社区型前端项目默认先定义页面范围，再开始实现。

最低建议页面集合：

- 社区首页
  - 推荐流、分区入口、热门内容、创作入口
- 视频详情页
  - 视频播放、简介、标签、作者信息、评论区、相关推荐
- 工作流详情页
  - 工作流说明、适用场景、参数信息、引用作品
- 作者主页
  - 作者资料、作品列表、工作流列表、动态或收藏
- 发布页
  - 上传视频、绑定工作流、填写标题与标签、选择分区

可选页面：

- 搜索页
- 分类页
- 通知页
- 个人中心
- 草稿箱

规则：

- 没有页面清单，不进入 `Build`
- 每次新增页面时，必须写清“这页解决什么问题”
- 所有页面按“主路径”优先，不先做边角页

## 8. 数据模型规则

社区项目前期至少定义 5 类核心实体：

- `User`
- `Video`
- `Workflow`
- `Post` 或 `FeedItem`
- `Comment`

推荐最小字段：

```ts
type User = {
  id: string
  name: string
  avatar: string
  bio?: string
}

type Video = {
  id: string
  title: string
  summary?: string
  cover: string
  videoUrl: string
  duration?: number
  tags: string[]
  authorId: string
  workflowId?: string
}

type Workflow = {
  id: string
  title: string
  summary?: string
  cover?: string
  authorId: string
}

type Comment = {
  id: string
  content: string
  authorId: string
  targetId: string
  createdAt: string
}
```

规则：

- 页面开发前，先确认当前页面依赖哪些实体
- 假数据结构要尽量贴近未来接口结构
- 不允许每个页面各自发明一套不同字段名
- 接口未接入前，也要统一字段命名

## 9. 组件约定

社区项目优先建立卡片系统，而不是先堆页面。

建议先抽出以下基础组件：

- 视频卡片
- 工作流卡片
- 作者卡片
- 评论项
- 标签组件
- 分区导航
- 发布表单模块

组件规则：

- 展示组件和数据组装逻辑尽量分开
- 卡片组件优先支持多场景复用
- 同类信息样式统一，不为单页临时发明特殊结构
- 复杂页面先由模块拼装，不把整页逻辑塞进一个文件

命名建议：

- `VideoCard`
- `WorkflowCard`
- `CreatorHeader`
- `CommentThread`
- `PublishFormSection`

## 10. 媒体资源规范

社区项目默认把视频和图片当高风险资源管理。

规则：

- 首页默认使用封面图或 hover 预览，不默认全量自动播放
- 长视频、原视频、预览视频分开处理
- 优先提供 `cover`、`poster`、`preview`，不要只给一个重视频地址
- 列表流里不要同时加载过多视频
- 视频资源优先走 CDN，不把大文件长期混在源码仓库里

推荐媒体字段：

```ts
type MediaAsset = {
  cover: string
  poster?: string
  preview?: string
  source?: string
}
```

交付前至少检查：

- 首屏媒体是否过重
- 是否存在重复打包
- 是否有无用的大文件留在仓库根目录
- 是否明确区分开发素材、展示素材、正式部署素材

## 11. 社区交互边界

社区前端最容易失控的是“假交互看起来像真功能”。

以下能力必须显式标记状态：

- 登录
- 注册
- 点赞
- 收藏
- 评论
- 关注
- 发布

每个交互都要明确属于哪一类：

- 纯前端占位
- 已接接口但未完整联调
- 已可用

规则：

- 占位交互必须在文档中说明
- 不允许把未接接口的交互伪装成已完成能力
- 评论、点赞、收藏这类能力优先统一交互反馈样式

## 12. 质量门槛

任何页面或模块在标记完成前，至少检查：

- 功能是否达到当前任务范围
- 主要路径是否可用
- 命名和目录是否清晰
- 是否存在明显占位未标记
- 是否留下下一步可继续的信息

前端社区项目额外检查：

- 桌面端是否正常
- 移动端是否正常
- 主要内容是否可读
- 资源体积是否明显失控
- 假数据、占位交互、未接接口是否已明确标注
- 主要卡片在列表中是否稳定
- 视频、封面、标签、作者信息是否层级清晰
- 评论区和发布链路是否至少具备一条完整主路径

## 13. 经验固化规则

只有下面两类内容进入 `memory/MEMORY.md`：

- 已验证有效的方法
- 已确认会重复出现的问题

每条经验建议固定格式：

```markdown
## 标题
- 场景：
- 结论：
- 证据：
- 适用范围：
```

不记录：

- 纯猜测
- 一次性临时现象
- 还没验证的习惯偏好

建议社区项目优先沉淀以下经验：

- 卡片信息密度如何控制
- 视频加载策略如何设计
- 评论区如何避免性能问题
- 工作流与视频如何绑定展示
- 移动端社区页如何保持可读性

## 14. 防中断规则

任何任务中断前，至少补 3 件事到 `progress.md`：

- 当前做到哪一步
- 卡住点是什么
- 下次第一步做什么

如果任务超过半天，建议补一条：

- 当前文件或页面入口路径

这样下一次可以直接继续，不需要重新摸索。

## 15. 升级条件

以下情况出现 2 项及以上，再考虑从轻量规则升级到完整规则体系：

- 多人长期协作
- 子模块超过 5 个
- 并行路线很多，容易反复试错
- 经验复用频繁
- 交付物不止前端代码，还包含文档、规范、模板、流程资产

升级时再引入：

- 更细的状态机
- 更完整的归档机制
- `genes/` / `capsules`
- 质量评分表

## 16. 推荐落地方式

如果是视频社区前端，建议这样用：

- `CLAUDE.md`
  - 写清项目目标、页面范围、数据模型、组件约定、媒体规范、数据接入边界
- `.codex/progress.md`
  - 记录首页、详情页、发布页、评论区、作者主页当前做到哪里
- `memory/MEMORY.md`
  - 记录卡片设计、视频加载、移动端适配、评论交互、接口对接中的有效经验

这类项目先保持轻量最重要。  
先把页面结构、内容链路、卡片系统、交互边界做对，再决定是否引入更重的规则机制。
