## 3. 我们已经考虑到的关键点

### 3.1 已明确考虑并已落地

- `requestId` 全链路基础能力
- 统一错误响应结构
- 上传归属不信任前端，统一以后端当前用户为准
- 后端兜底校验上传大小、类型、状态、路径
- 媒体统一建模为 `media_assets`
- 软删除基础结构
- 本地日志文件拆分与滚动切分

### 3.2 已考虑但还没做到上线级

- 日志集中上报到 ELK/云日志平台
- 数据备份、冷热归档、恢复演练
- 外部供应商错误码映射体系
- 更完整的稳定性基建：限流、幂等、失败重试清理

### 3.2.1 关于日志平台查询准备

- 当前已经具备 `requestId` 基础链路，且请求与响应都会带 `X-Request-Id`
- 当前又补了 `traceId` 基础层：兼容 `X-Trace-Id` 与 `traceparent`，并在响应头回写 `X-Trace-Id`
- 当前日志格式已经统一输出 `traceId / requestId / userId`
- 当前又补充了后端解析后的真实 `userId` 到 MDC 和日志格式
- 这意味着即使现在日志还未上阿里云，字段口径已经开始向“可按 `traceId / requestId / userId` 查日志”对齐
- 仍然保持红线：日志里的 `userId` 只能来自后端解析后的当前用户，不能信任前端传参

### 3.2.2 `requestId` 和 `traceId` 的职责划分

- `requestId` 负责定位“某一次具体请求”，更适合前端报错、接口回放、客服或测试反馈问题时直接贴出来
- `traceId` 负责定位“一次业务动作的整条链路”，更适合后续串异步任务、Python Worker、审核回调、管理后台操作审计
- 当前 DramaTV 已有 `traceId` 基础层，但还没有 `spanId`、跨服务自动透传、完整链路平台集成，因此仍处于“为后续上云和链路追踪做准备”的阶段
- 对标画布当前在阿里云日志平台按 `traceId + userId` 查问题的方式，DramaTV 现在已经把字段口径准备好了，但后续还要继续补齐异步链路透传和下游服务接入

### 3.3 当前还不建议过早做重的部分

- 为了“模拟大厂”而提前自建复杂日志平台
- 在本地阶段提前做复杂归档系统
- 在没有真实外部依赖时，先堆完整供应商错误码映射层

## 4. AOP 现状

| 项目 | 当前结论 |
| --- | --- |
| 自定义业务 AOP 切面 | 没有 |
| `@Aspect / @Around / @Before / @After` | 没有发现 |
| `spring-boot-starter-aop` | 未显式引入 |
| Spring 事务代理 | 有，当前通过 `@Transactional` 在用 |
| 当前横切能力主要实现方式 | `Filter + ControllerAdvice + Logback/MDC + Transaction Proxy` |

结论：

- 当前项目没有“我们自己写的业务 AOP 切面”
- 但存在 Spring 事务代理这一类框架层 AOP 能力
- 现在的横切逻辑主要不是靠 Aspect，而是靠：
  - 请求过滤器
  - 统一异常处理
  - 日志上下文
  - 事务注解

### 4.1 AOP 在本项目里有没有必要

结论：

- 不是完全没必要
- 但当前阶段没有必要为了“显得高级”而主动引入一套自定义 AOP 体系
- 你理解的方向基本对，AOP 适合做“横切的通用能力”，但不适合承载核心业务流程

更准确地说，AOP 适合解决的是这些问题：

- 某类日志、埋点、审计要加在很多方法上
- 某类方法都要统一做幂等、防重、耗时统计
- 某些后台操作都要自动记录操作人、目标对象、结果

但以下内容不建议因为用了 AOP 就硬塞进切面：

- 核心业务分支
- 权限校验主逻辑
- 复杂发布流程编排
- 依赖上下文很重的数据库写链路

对 DramaTV 当前阶段的建议是：

- `requestId`、`userId`、访问日志：继续用 `Filter + MDC`
- 统一错误码与异常收口：继续用 `ControllerAdvice`
- 事务：继续用 `@Transactional`
- 如果后续管理后台要补“操作审计日志 / 方法耗时埋点 / 注解式幂等防重”，那时再引入自定义 AOP，会更合适

## 5. 结合当前项目的判断

从当前阶段看，DramaTV 社区后端已经具备了比较像正式项目的基础骨架：

- 有统一请求 ID
- 有统一错误响应
- 有统一媒体资产模型
- 有登录态驱动的真实用户归属
- 有上传安全兜底
- 有软删除基础
- 有本地可观测日志

但距离“完整上线级后端”还差以下几类能力：

1. 日志集中上报与查询平台
2. 备份、归档、恢复策略
3. 更系统的限流、幂等、自动化 smoke
4. 真实云存储 OSS provider 接入
5. 对外部依赖的统一错误码映射

## 6. 当前建议优先级

建议按以下顺序继续推进：

1. 先完成 `O3`，把 OSS provider 接入点和媒体存储抽象收完整
2. 再做 `O4`，补限流、幂等、自动 smoke、失败清理
3. 然后和运维对齐日志平台、数据库备份、对象存储策略
4. 最后再根据真实接入的外部依赖补错误码映射体系

### 6.1 数据堆积的分阶段规划建议

#### 当前阶段

- 用户量小，优先保证功能正确、表结构可扩展、日志和状态字段齐全
- 不急着做复杂冷热分离
- 但新增数据表、媒体表、异步任务表时，要避免把“删除、归档、状态流转”彻底写死

#### 测试环境 / 小规模阶段

- 明确数据库备份频率
- 明确媒体资产和对象存储保留策略
- 明确失败任务、过期草稿、无效上传记录的清理策略

#### 后续增长阶段

- 再逐步补历史归档、冷热分层、对象存储备份、恢复演练
- 这类能力更适合在运维资源和真实数据规模起来后推进
