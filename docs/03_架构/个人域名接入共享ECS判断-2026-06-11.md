# 个人域名接入共享 ECS 判断
创建日期：`2026-06-11`
适用环境：`8.141.20.130` 共享测试 ECS

## 1. 结论

当前不建议把**个人域名**直接作为这台**公司中国内地阿里云 ECS** 上 DramaTV 社区的正式公网入口。

这不是前端、后端或 Nginx 配置优先级问题，核心是：

- 域名持有者
- 备案主体
- 实际接入商
- 实际部署资源

这四者需要按当前真实部署关系对齐。

## 2. 官方依据

2026-06-11 查阅阿里云官方备案文档后，得到以下稳定口径：

1. 使用阿里云中国内地云资源时，备案需通过**实际接入商阿里云**完成。
2. 接入备案时，如果**域名与备案主体不一致**，需要先修改域名所有者信息，再接入备案。
3. 备案订单需要关联**实际使用的阿里云服务器实例**或**备案服务码**。

## 3. 落到当前场景的判断

如果你的域名当前属于**个人主体**，而这台 ECS 属于公司环境，且后续希望把社区作为公司项目长期挂在这台机器上，那么：

- 技术上即使短时能解析到机器，也不等于这是一个可持续的正式入口。
- 域名即使“已经备案过”，也不代表它天然适合当前这条接入链路。
- 一旦当前真实的接入关系、备案主体、域名持有者没有重新对齐，后续仍可能卡在阿里云接入备案、入口校验或正式切换阶段。

## 4. 能不能“先试试”

如果“试试”的意思是：

- 直接把个人域名公开解析到这台中国内地 ECS
- 然后把它当社区正式访问地址来用

当前不建议这样做。

如果“试试”的意思是：

- 提前演练后续换域名时的 Host 分流
- 验证 Nginx、前后台路由、资源链路、跳转和证书准备方式

这个可以做，但建议只做**内部演练**，不要直接做公网正式切换。

## 5. 建议的安全演练方案

建议按下面的方式练手：

1. 不先把个人域名作为正式公网入口。
2. 在社区自己的 Nginx 配置中，为该域名增加独立 `server_name`。
3. 使用本地 `hosts` 或 `curl --resolve` 做 Host 分流验证。
4. 只验证：
   - 前台首页是否命中社区项目
   - 后台 `/admin` 是否命中社区后台
   - `/api`、`/media`、登录跳转、静态资源是否正常
5. 等公司正式域名准备好后，再切到公司主体域名，补齐：
   - 备案/接入备案
   - 80/443 放行
   - HTTPS 证书
   - Nginx 正式站点配置

## 6. 后续切公司域名时的检查顺序

后续公司正式域名到位后，优先检查：

1. 域名持有者是不是目标主体。
2. 该域名能否在阿里云按目标主体完成新增备案或新增接入备案。
3. 域名是否作为社区项目的独立 `server_name` 挂载，而不是继续走裸 IP 或共享兜底入口。
4. 阿里云安全组、ECS 防火墙、证书与 Nginx 是否同步收口。

## 7. 一句话判断

个人域名可以拿来做**内部 Host 演练**，但不应作为这台公司中国内地共享 ECS 的长期正式公网入口；正式切换应等公司主体域名和阿里云备案接入口径一起对齐后再做。
