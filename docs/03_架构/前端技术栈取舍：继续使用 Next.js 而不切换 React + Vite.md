# 前端技术栈取舍：继续使用 Next.js 而不切换 React + Vite

更新日期：2026-04-15

## 1. 文档目的

这份文档用于回答一个很实际的问题：

- 既然我们现在要用新的视觉方案重构社区前端，是否应该顺手把正式前端从 `Next.js` 换成 `React + Vite`

这不是抽象的技术偏好讨论，而是基于当前仓库真实代码状态、真实联调方式、真实发布链路做的判断。

## 2. 结论先行

当前阶段不建议把正式前端主线从 `Next.js` 切到 `React + Vite`。

更合理的方案是：

- 继续保留 `apps/web` 作为正式前端主线
- 把同事的 `mindloop-_-cinematic-archive (1)` 当作视觉母版和动效参考
- 在现有 `apps/web` 内重构页面视觉和组件层
- 继续复用已经打通的真实后端接口、发布链路、互动链路和页面路由

一句话判断：

- 如果只是做纯前端原型，`React + Vite` 更轻更快
- 但对我们这个已经进入全链路开发的社区项目，继续沿用 `Next.js` 反而更省成本、更稳

## 3. 当前仓库的真实状态

当前正式主线已经不是“前端原型”阶段，而是“真实页面 + 真实接口 + 真实交互闭环”阶段。

### 3.1 正式工程主线

- 正式前端：`apps/web`
- 正式后端：`apps/server`
- 当前统一口径已经在 [AGENTS.md](../../AGENTS.md) 固定为 `apps/web + apps/server`

### 3.2 当前前端不是普通 React SPA

现有前端已经明显建立在 `Next.js app router` 上，而不是单纯的 React 组件集合。

直接证据：

- 路由目录已经是 `app/` 结构
- 多个页面通过服务端路由直接取数
- 动态详情页依赖 `notFound()`
- 社区层使用了 `layout.tsx`
- 发布、点赞、收藏、评论等交互已经用了 `use server`

可直接参考：

- `apps/web/src/app/(community)/page.tsx`
- `apps/web/src/app/(community)/videos/[id]/page.tsx`
- `apps/web/src/app/(community)/workflows/[id]/page.tsx`
- `apps/web/src/app/(community)/me/page.tsx`
- `apps/web/src/app/(community)/layout.tsx`
- `apps/web/src/features/publish/actions.ts`
- `apps/web/src/features/community-interactions/actions.ts`
- `apps/web/src/features/discussions/actions.ts`

### 3.3 当前数据层已经是“真后端对接”

当前 `apps/web` 已经通过统一的社区服务层对接后端，而不是依赖 mock 页面数据。

核心入口：

- `apps/web/src/lib/api/community-service.ts`

这个服务层已经承担了：

- 请求 `Spring Boot` 后端
- 统一处理 `X-Request-Id`
- 统一处理错误码和错误信息
- 首页、详情、发布、评论、点赞、收藏、关注、上传、个人中心等多个业务请求

这说明当前前端不是“随便换一个脚手架”那么简单，而是已经有一套正在工作的真实交互边界。

## 4. 为什么 React + Vite 看起来更方便

从纯前端体验上说，`React + Vite` 的确有几个优势：

- 启动更轻
- 结构更简单
- 对纯 SPA 原型开发很顺手
- 更适合快速搭视觉稿、演示稿、活动页、单页站点

同事的原型项目就是这个类型：

- 目录：`mindloop-_-cinematic-archive (1)`
- 技术栈：`Vite + React + TypeScript`
- 页面主要集中在 `src/App.tsx`
- 视觉样式主要集中在 `src/index.css`
- 里面大量使用本地 mock 数据和前端内存态切页

也就是说，这套原型非常适合做下面这些事情：

- 先把风格做出来
- 先把卡片、hero、背景氛围、排版语气做出来
- 先验证“页面看起来够不够好”

但它不适合作为我们现在正式工程的直接替代品。

## 5. 为什么当前不建议切换

### 5.1 切栈不是“换个脚手架”，而是重做应用层

如果从 `Next.js` 切到 `React + Vite`，需要重做的不是页面样式，而是应用基础设施：

- 路由体系要从 `app router` 改成 `react-router`
- 服务端取数要改成浏览器取数或再搭一层 BFF
- `use server` action 要全部改写成前端直接调接口
- `revalidatePath` 要改成自己维护缓存失效和刷新策略
- `notFound()`、动态路由、错误页处理要重新组织
- 首屏数据获取方式要改
- 部分请求可能会引出新的跨域、cookie、鉴权、代理问题

这类改动不产生新的业务价值，但会显著扩大切换成本。

### 5.2 当前项目已经深度使用 Next.js 的能力

当前代码里最关键的不是“用了 React”，而是已经用了 `Next.js` 的应用层能力。

典型例子：

- 发布页服务端预取：`apps/web/src/app/(community)/publish/page.tsx`
- 发布动作使用 `use server` 和 `revalidatePath`：`apps/web/src/features/publish/actions.ts`
- 互动动作使用 `use server`：`apps/web/src/features/community-interactions/actions.ts`
- 讨论动作使用 `use server`：`apps/web/src/features/discussions/actions.ts`

如果切到 `React + Vite`，这些能力要么全部重写，要么自己补一套替代机制。

### 5.3 当前主问题是视觉层，不是工程层

我们现在真正不满意的是：

- 首页和主线页面视觉不够好
- 需要把同事那套 cinematic 风格迁进来

我们现在并不缺：

- 前端运行主线
- 真实接口接法
- 路由框架
- 发布和互动的基础闭环

所以问题应该定义为：

- “重构 UI 和信息架构”

而不是：

- “重建前端应用框架”

### 5.4 切换会拖慢全链路开发

当前我们已经明确进入全链路开发阶段，且用户口径已经固定：

- 不再使用 mock 作为正式能力
- 要围绕真实后端持续推进
- 要按小切片逐步把功能做实

在这个阶段切到 `React + Vite`，会直接带来两个后果：

- 研发时间被迁移成本吞掉
- 现有联调稳定性被重新打散

这会让“页面变好看”这件事反而更慢落地。

## 6. 专业解释

从专业角度说，`Next.js` 和 `React + Vite` 不在同一层。

### 6.1 它们分别是什么

- `React` 是 UI 库
- `Vite` 是开发服务器和构建工具
- `Next.js` 是基于 React 的全栈应用框架

所以严格说：

- `React + Vite` 是“自己组装应用能力”
- `Next.js` 是“框架已经把应用能力组织好了”

### 6.2 对我们项目的实际差异

`Next.js` 当前为我们提供了这些已经落地在代码里的能力：

- 文件路由
- 动态路由
- 服务端页面入口
- `layout`
- `notFound`
- `use server`
- `revalidatePath`
- 更清晰的页面级数据边界

`React + Vite` 并不是做不到，而是这些能力需要我们自己补：

- 路由库自己选
- 数据预取方式自己定
- 页面缓存和刷新自己做
- action 层自己封装
- 404 和错误边界自己补
- 页面级加载策略自己设计

这就是为什么对于纯页面原型，Vite 很轻；但对于正式应用，Next 的工程收益会更高。

## 7. 通俗解释

可以把这两套理解成下面两个东西：

- `React + Vite` 像毛坯房，装修上手很快，想怎么搭都行
- `Next.js` 像已经接好水电、门牌、管线和物业规则的精装框架

如果我们现在只是画效果图、拍样板间照片，那毛坯房很方便。

但我们现在已经不是在画效果图，而是已经开始住人了：

- 首页在用
- 详情页在用
- 发布链路在跑
- 点赞评论收藏在接
- 个人中心已经挂上真接口

这时候为了“装修更顺手一点”去整套搬家，通常比继续在现有房子里改造更慢。

## 8. 两套方案对比

| 维度 | 继续使用 `Next.js` | 切到 `React + Vite` |
| --- | --- | --- |
| 保留现有联调成果 | 高 | 低 |
| 页面视觉重构效率 | 高 | 中 |
| 首次上手纯前端开发 | 中 | 高 |
| 改造正式业务成本 | 低 | 高 |
| 对发布/互动链路影响 | 小 | 大 |
| 对路由体系影响 | 小 | 大 |
| 对缓存与刷新策略影响 | 小 | 大 |
| 对当前排期风险 | 低 | 高 |
| 是否符合当前仓库主线 | 是 | 否 |

## 9. 什么情况下切到 React + Vite 才合理

下面这些前提同时成立时，切栈才更像是正确决策：

- 项目仍处在纯视觉原型阶段
- 还没有真实后端联调压力
- 没有形成稳定的路由和服务端页面结构
- 不依赖 `server actions`
- 不在乎首屏、详情页结构、页面级数据组织
- 团队明确决定以后就是纯 SPA 模式

但我们当前并不满足这些前提。

## 10. 同事那套 Vite 原型应该怎么用

正确使用方式不是“拿来替换正式工程”，而是：

- 当作视觉母版
- 当作动效、氛围、排版、卡片样式参考
- 当作页面情绪板和视觉语言来源

不应该直接继承的部分：

- mock 数据结构
- `currentPage` 这种前端内存态切页方式
- 把 `prompt / tool / work / workflow` 混成同级内容类型的产品建模

应该提取的部分：

- hero 区结构
- 背景视频和氛围层
- 深色 cinematic 视觉语气
- 字体层级
- 卡片密度
- 页面滚动节奏
- 局部动效

## 11. 对当前项目的执行建议

当前建议按下面方式推进：

### 11.1 不改正式技术栈

- 正式前端继续使用 `apps/web`
- 不新建第二套正式前端主线
- 不把 Vite 原型直接变成生产应用

### 11.2 在 `apps/web` 内做 UI v2 重构

优先重构这些页面：

- 社区首页
- 视频详情页
- 作者主页
- 个人中心页
- 发布页
- 讨论页

并继续保留以下特殊页面独立演进：

- `/nano-banana`
- `/seedance`

### 11.3 以真实接口为硬约束

重构时必须继续复用：

- `apps/web/src/lib/api/community-service.ts`
- 现有 contracts
- 现有 mappers
- 现有 `Spring Boot` API

规则是：

- 可以重写视觉
- 可以重写布局
- 可以重写组件层
- 不要轻易重写已经工作的真实接口对接边界

## 12. 最终决策

最终决策固定为：

- 当前不切换正式前端技术栈
- 正式主线继续使用 `Next.js + React + TypeScript`
- `React + Vite` 原型仅作为视觉参考和动效母版
- 新版社区页面在 `apps/web` 内重构，并继续对接现有真实后端

这份决策的核心不是“偏好 Next.js”，而是：

- 在当前全链路开发阶段，继续保留正式工程主线，能用最小代价换到最大的可交付结果
