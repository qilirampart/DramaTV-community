# DramaTV社区后台拆分与端口规划

## 1. 当前范围

这份文档只讨论 `DramaTV 社区后台一期`，不把画布后台一起纳入本轮实施。

当前固定边界如下：

- 后台只服务社区内容治理、运营配置、账号管理和审核处理。
- `工作流` 在当前阶段只按社区侧内容对象处理。
- 当前后台不进入真实画布 runtime、节点图、执行记录、画布空间管理。
- 和画布有关的部分，只保留 `绑定关系`、`展示信息`、`入口占位`。

一句话定性：

- 现在做的是 `社区后台`
- 不是 `社区 + 画布统一后台`

## 2. 一句话方案

当前最合适的工程方案是：

- 社区前台和社区后台拆成两个独立前端应用。
- 这两个前端不是两套独立产品，而是同一条社区产品线下的两个操作面。
- 后台一期继续复用现有 `apps/server`，通过 `/api/admin/**` 提供后台接口。
- 社区前台与社区后台共享同一套社区业务数据库、同一套领域模型、同一条发布审核治理主链路，但都只能通过后端 API 写入。
- 工作流在后台里仍然是 `社区展示对象`，不是画布 runtime 对象。

## 3. 工程拆分

## 3.1 应用划分

- `apps/web`
  - 社区前台
  - 面向普通用户、创作者
- `apps/admin`
  - 社区后台
  - 面向管理员、运营、审核人员
- `apps/server`
  - 社区统一后端
  - 同时承接前台 API 和后台 API

当前不建议再做这些方案：

- 把后台页面继续塞回 `apps/web`
- 为后台单独再起一套 Java 服务
- 提前把画布后台也并进来一起做

## 3.2 为什么这样拆

这样拆的收益是明确的：

- 前后台职责清晰，页面和权限不会继续搅在一起。
- 本地开发可以独立启动、独立验收、独立部署。
- 后端先不拆服务，能降低一期改造成本。
- 后续真要接画布后台时，也不会反过来污染社区后台边界。

## 3.3 当前固定策略

当前这轮必须明确按“`工程分区，业务一体`”推进：

- `apps/web`
  - 面向普通用户、创作者
- `apps/admin`
  - 面向管理员、运营、审核人员
- `apps/server`
  - 同时承接社区前台与后台管理的统一业务后端

这句话的实际含义是：

- `apps/web` 和 `apps/admin` 必须保持两个独立前端应用，不回到“全塞进一个 Next 应用”的做法。
- 但它们也不是两套互不相干的系统，而是共享同一个社区领域。
- `User / Video / Workflow / FeedItem / Comment` 这套核心实体，不允许前后台各自再造一套平行模型。
- 发布、审核、举报、评论治理、运营排序这几条链路，要视为同一套业务状态流，不按“前台一套、后台一套”拆开建设。
- 后台为了治理方便补充管理表可以接受，但不能反过来把社区主数据复制成一套后台专用内容体系。

## 4. 本地端口规划

## 4.1 当前已存在

- 社区前台主线：`3106`
- 社区前台云镜像：`3107`
- 社区后端：`18080`

## 4.2 后台新增规划

- 社区后台主线：`3206`
- 社区后台云镜像：`3207`

## 4.3 固定规则

- `31xx` 给社区前台
- `32xx` 给社区后台
- `18xxx` 给社区统一后端

这样后面看到端口就能立刻判断环境和职责。

## 5. 云上入口规划

正式部署时，前后台也应保持入口分离。

建议口径：

- 社区前台：`community.xxx.com`
- 社区后台：`admin-community.xxx.com`
- 社区后端：走 Nginx 反向代理到 `apps/server`

测试阶段即使还没有正式域名，也建议按这个思路配：

```text
community.xxx.com        -> 127.0.0.1:3106
admin-community.xxx.com  -> 127.0.0.1:3206
api internal             -> 127.0.0.1:18080
```

## 6. 数据边界

## 6.1 社区前台与社区后台

这两者应共享同一套社区业务数据。

共享方式：

- 共享同一个 PostgreSQL 实例
- 共享同一套社区业务表
- 共享同一套社区领域模型和状态定义
- 统一通过 `apps/server` 写入

不建议：

- 后台前端直连数据库
- 前后台各维护一套相互同步的数据副本

## 6.2 工作流对象的当前边界

后台当前看到的 `工作流`，本质上是社区里的一个内容对象。

一期只管理这些字段：

- 标题
- 简介
- 封面
- 示例视频
- 作者
- 标签
- 是否允许复制
- 关联作品
- 审核状态
- 展示排序

一期不管理这些东西：

- 画布节点图 JSON
- 运行时参数
- 执行任务链路
- 画布项目结构
- 画布空间资产

## 6.3 可复用表

后台一期优先复用现有社区表：

- `users`
- `publish_drafts`
- `audit_records`
- `report_tickets`
- `comments`
- `media_assets`
- `feed_items`
- `async_task_records`

## 6.4 可能新增的后台表

为了让后台真正可用，建议预留这几张后台侧表：

- `admin_operation_logs`
  - 记录谁在后台做了什么操作
- `admin_feed_slot_configs`
  - 记录首页、精选、讨论区的人工排序与运营位配置
- `admin_role_bindings`
  - 如果现有 `users.role_code` 不够表达后台角色，再单独补这张

一期里最有必要优先落的是前两张。

## 7. 后台一期页面范围

建议第一批页面固定为：

- `/login`
  - 后台登录
- `/dashboard`
  - 基础概览
- `/users`
  - 账号管理
- `/moderation`
  - 内容审核中心
- `/reports`
  - 举报工单中心
- `/comments`
  - 评论治理中心
- `/feed-ops/home`
  - 首页运营排序
- `/feed-ops/featured`
  - 精选页运营排序
- `/feed-ops/discussions`
  - 讨论区运营排序
- `/taxonomy`
  - 标签、分区、分类管理
- `/media-tasks`
  - 媒体与异步任务排查
- `/audit-logs`
  - 后台操作审计日志

## 8. 后台 API 分组

后台 API 一期统一落在现有 `apps/server` 下。

建议分组如下：

- `/api/admin/auth/**`
- `/api/admin/dashboard/**`
- `/api/admin/users/**`
- `/api/admin/moderation/**`
- `/api/admin/reports/**`
- `/api/admin/comments/**`
- `/api/admin/feed-ops/**`
- `/api/admin/taxonomy/**`
- `/api/admin/media-tasks/**`
- `/api/admin/audit-logs/**`

这样做的好处：

- 路由语义清楚
- 权限控制容易挂
- 后面真要拆后台服务时，迁移边界也清楚

## 9. 本地开发链路

## 9.1 社区前台链路

```text
http://127.0.0.1:3106 -> apps/web -> http://127.0.0.1:18080
```

## 9.2 社区后台链路

```text
http://127.0.0.1:3206 -> apps/admin -> http://127.0.0.1:18080/api/admin/**
```

## 9.3 云镜像链路

```text
http://127.0.0.1:3107 -> 云后端镜像
http://127.0.0.1:3207 -> 后续后台云镜像
```

## 10. 落地顺序

### Phase 1

- 新建 `apps/admin`
- 跑通 `3206`
- 先做后台登录壳子和基础路由守卫

### Phase 2

- 落 `/api/admin/auth/**`
- 落 `/users`
- 先完成账号管理最小闭环

### Phase 3

- 落 `/moderation`
- 落 `/reports`
- 落 `/comments`

### Phase 4

- 落 `/feed-ops/**`
- 落 `/taxonomy`

### Phase 5

- 落 `/media-tasks`
- 落 `/audit-logs`
- 再补 dashboard 指标聚合

## 11. 当前结论

当前可直接开工的方案已经固定：

- 新建 `apps/admin`
- 本地端口固定 `3206`
- 后台一期继续复用 `apps/server`
- 后台接口统一走 `/api/admin/**`
- 工作流继续按社区占位内容处理
- 本轮不进入画布 runtime 后台建设

后续如果真要和画布后台联动，也应该在社区后台一期做完之后，再通过更清晰的领域边界来接，而不是现在提前混做。
