# 社区三类主内容与后端资源组合方案

更新时间：2026-04-21

## 1. 结论

DramaTV 社区前台主内容应固定为三类：

| 前台主内容 | 用户理解 | 后端组合 |
| --- | --- | --- |
| `Prompt 内容` | 图片或视频结果 + 提示词 | `prompt_entries` + `prompt_example_links` + `media_assets` |
| `工作流作品` | 视频作品 + 可复用工作流，后续进入画布 | `videos.workflow_id` + `workflows` + `canvas_*` |
| `讨论帖子` | 独立 Markdown 讨论内容 | `discussion_threads` + `comments` + 可选正文媒体附件 |

这三类是产品分类，不等于数据库表名，也不等于资源类型。

核心原则：

- 前台按三类主内容组织页面、筛选、卡片和汇报口径。
- 后端按领域实体保存真实数据。
- 图片、视频、封面、preview、source 都属于 `media_assets` 资源层，不单独成为社区主内容。
- 后端需要一层内容索引或聚合层，把领域实体组合成前台三类内容。

## 2. 为什么不能按图片、视频、工作流、帖子平铺

`视频` 这个词在当前项目里有两种身份：

| 场景 | 视频的身份 | 产品分类 |
| --- | --- | --- |
| 视频 Prompt 示例 | 提示词生成结果的示例资源 | `Prompt 内容` |
| 成片作品并绑定工作流 | 社区作品本体，展示效果并指向方法 | `工作流作品` |

如果把 `video` 直接作为前台一级分类，会导致：

- 视频 Prompt 和工作流作品混在一起。
- 工作流会被误解为和 Prompt、帖子并列的第四类主内容。
- 图片、视频等资源容易被误当成内容，而不是内容引用的资产。
- 后续上线时，媒体存储、审核、搜索、推荐、画布复制会继续绕在一起。

因此，前台应看“内容意图”，后端再组合资源。

## 3. 当前后端实际方案

当前后端已经具备本地闭环，但模型口径仍是混合状态。

### 3.1 已经合理的部分

- `prompt_entries` 已经承接 Prompt 内容，`modality=image/video` 区分图片 Prompt 和视频 Prompt。
- `prompt_example_links` 把 Prompt 与示例资源关联起来。
- `videos.workflow_id -> workflows.id` 已经能表达视频作品绑定工作流。
- `discussion_threads` 已经承接帖子。
- `media_assets` 只保存媒体元数据，不保存大二进制本体。
- `comments`、`interaction_actions` 已经通过 `target_type + target_id` 支持多对象评论、点赞、收藏。
- `audit_records`、`report_tickets`、`async_task_records`、`canvas_copy_tasks` 等表已为审核、举报、异步和画布联动预留边界。

### 3.2 仍需收口的部分

当前还有一些工程类型直接暴露到前台聚合逻辑：

- `feed_items.item_type` 当前可能是 `video / workflow / prompt`。
- 首页聚合会分别加载 `loadPublishedVideoFeed()`、`loadPublishedWorkflowFeed()`、`loadPublishedPromptFeed()`。
- 前端接口契约里 `ApiFeedHomeResponse.items[].itemType` 仍是 `video | workflow | prompt`。
- 互动目标类型仍是 `video / workflow / prompt / post / comment`。

这些类型对后端实现是有意义的，但不应继续作为前台产品分类。

## 4. 推荐后端方案

推荐采用：

> 领域实体分表存储 + 统一内容索引层 + 媒体资源独立存储。

不建议把所有内容合并成一张大表。原因是三类内容字段差异明显：

- Prompt 需要提示词正文、语言版本、模型、示例资源。
- 工作流作品需要视频资源、绑定工作流、画布复制能力。
- 帖子需要 Markdown 正文、频道、回复流。

如果强行一张大表，会出现大量空字段和 JSON 黑盒，后续审核、搜索、推荐、权限和画布联动都会变复杂。

### 4.1 建议新增或强化的内容索引层

建议后续把 `feed_items` 升级为更清晰的 `content_items` 或新增同类表：

```sql
content_items
- id
- content_kind: prompt | workflow_work | post
- target_type: prompt | video | post
- target_id
- author_id
- title
- summary
- cover_asset_id
- visibility
- publish_status
- moderation_status
- rank_score
- published_at
- created_at
- updated_at
```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `content_kind` | 前台产品分类，固定三类：`prompt / workflow_work / post` |
| `target_type` | 后端真实实体类型：`prompt / video / post` |
| `target_id` | 真实实体 ID |
| `cover_asset_id` | 前台卡片默认封面资源 |
| `rank_score` | 首页、精选、榜单排序用 |
| `moderation_status` | 后续审核后台统一处理 |

映射关系：

| content_kind | target_type | 真实表 |
| --- | --- | --- |
| `prompt` | `prompt` | `prompt_entries` |
| `workflow_work` | `video` | `videos`，并通过 `workflow_id` 找 `workflows` |
| `post` | `post` | `discussion_threads` |

这样前台只需要理解三类内容，后端仍然保留清晰领域表。

### 4.2 互动目标的处理

短期可以继续使用现有：

- `comments.target_type + target_id`
- `interaction_actions.target_type + target_id`

但应把目标类型分两层理解：

| 层级 | 类型 |
| --- | --- |
| 产品内容类型 | `prompt / workflow_work / post` |
| 后端实体目标 | `prompt / video / workflow / post / comment` |

短期不用马上迁移互动表。中期可以在服务层增加 `ContentTargetResolver`，把前台内容类型解析成真实实体目标，避免业务代码里到处 switch。

## 5. 三类内容的资源组合

### 5.1 Prompt 内容

组成：

- `prompt_entries`：标题、摘要、提示词正文、`modality`、标签、作者、状态。
- `prompt_example_links`：Prompt 与示例资源的多对多关系。
- `media_assets`：示例图片、示例视频、封面。

说明：

- `modality=image` 表示图片 Prompt。
- `modality=video` 表示视频 Prompt。
- 视频 Prompt 里的视频是示例资源，不是工作流作品。

### 5.2 工作流作品

组成：

- `videos`：视频作品本体，封面、poster、preview、source、播放时长、统计。
- `workflows`：工作流说明、可复制状态、画布绑定入口。
- `canvas_bindings`、`canvas_workflow_runtimes`、`canvas_copy_tasks`：后续画布复制和打开。
- `media_assets`：视频源文件、封面、预览、poster。

说明：

- 这里的主内容是“视频作品 + 工作流方法”。
- 工作流可以有详情页，但在社区主分发里应作为作品方法层，不建议继续被讲成第四类主内容。

### 5.3 讨论帖子

组成：

- `discussion_threads`：标题、Markdown 正文、频道、标签、作者、发布时间。
- `comments`：回复和评论。
- `media_assets`：后续正文插入图片、视频时可作为附件资源。

说明：

- 帖子是独立内容，不是视频或工作流的附属评论。
- 帖子可以讨论 Prompt、视频、工作流，但默认不应强制绑定对象。

## 6. 图片中提到的问题当前是否已注意

| 问题 | 当前状态 | 说明 |
| --- | --- | --- |
| 注册后是否需要补充资料 | 部分完成 | 当前有登录、用户、作者主页和 `creator_profiles`，但没有完整注册资料补全流程。后续接公司画布登录后再统一。 |
| 审核怎么处理 | 已预留，未完成 | 有 `audit_records` 和内部审核回调接口，但没有审核后台、队列、人审流程、风控策略。 |
| 图片和视频存哪里 | 本地可用，云化未完成 | 当前本地 `tmp/media` 和 `media_assets` metadata 可用，上线应迁到 OSS/S3/MinIO + CDN。 |
| 大文件是否进数据库 | 已规避 | 当前设计明确数据库不保存大视频、大图片二进制，只保存 metadata 和 object key。 |
| 上传是否异步 | 已预留，未生产化 | 有 `async_task_records`、内部回调接口和媒体处理边界，但正式转码、抽帧、preview 生成还没落地。 |
| 首页是否全量自动播放 | 已注意 | 规则上已明确列表不全量自动播放，前端也已改过悬浮播放和少量 hero 自动播放。 |
| 画布怎么对接 | 已预留，未真实对接 | 有画布入口、runtime 占位、copy task 表，但还没接公司真实登录和真实画布复制 API。 |
| 评论点赞收藏是否真实 | 已完成本地闭环 | 当前视频、工作流、Prompt、帖子已接真实后端互动。 |
| 搜索推荐怎么做 | 未完成 | 当前是业务查询和简单排序，后续需要搜索索引、运营精选配置和真实排序信号。 |
| 线上运维和排障 | 部分完成 | 已有 requestId 和本地日志分文件，线上日志采集、告警、指标、慢查询面板未完成。 |

## 7. 推进建议

### 短期

- 文档、表格、页面文案统一改成三类主内容：`Prompt 内容 / 工作流作品 / 讨论帖子`。
- 首页和精选页筛选不要再把 `video` 当独立前台分类。
- 工作流在分发层优先作为“工作流作品”的方法入口展示。

### 中期

- 新增或升级统一内容索引层，字段中同时保留 `content_kind` 和 `target_type`。
- 首页、精选、作者页、搜索、推荐统一读取内容索引层。
- 互动、审核、举报、通知、搜索都通过内容索引层拿统一上下文。

### 上线前

- 接公司画布登录。
- 上传改 OSS 预签名直传。
- 视频处理接异步队列和 Worker。
- 审核后台独立建设。
- 对象存储、CDN、日志采集、告警和备份恢复上线。
