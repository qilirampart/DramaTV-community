# DramaTV 社区后台管理系统规划

## 1. 背景

### 当前范围说明

当前这份后台规划先只服务 `DramaTV 社区` 本身，不把画布后台一起纳入一期范围。

这意味着：

- 当前后台先只管社区内容与社区治理
- `工作流` 在后台里先按“社区展示内容对象”管理
- 不进入真实画布 runtime 管理、节点图管理、画布执行管理
- 和画布相关的部分先只保留审核位、展示位、绑定位

一句话：

- 当前先做 `社区后台`
- 工作流先按 `占位型社区内容` 处理

社区前台这一阶段已经基本跑通：

- 首页、精选、讨论区、详情页、作者页、发布页已经有真实前后端链路
- 登录、点赞、收藏、评论、发帖、发布提示词/工作流已经具备基础闭环
- 云测试环境、OSS、RDS、Redis、媒体代理、异步任务也已经开始接入

下一阶段的重点，不应再继续堆前台页面，而是补齐“可运营、可治理、可控”的后台系统。

后台系统的目标不是做一个很重的企业中台，而是先解决当前社区最现实的 5 类问题：

1. 谁能发，谁能看，谁能管
2. 发出来的内容怎么审核、下线、恢复
3. 用户举报后谁来处理
4. 首页、精选、讨论区内容怎么人工运营排序
5. 异步媒体、封面、上传、任务失败时谁来排查

## 2. 设计原则

### 2.1 单独建设，不塞进社区前台

后台管理系统应作为独立入口建设，不继续塞进现有社区前台页面。

- 前台：给普通用户、创作者使用
- 后台：给运营、审核、管理员使用

### 2.2 先做运营治理闭环，不先做大而全

第一版后台先围绕当前社区已有对象展开，不先做复杂推荐、BI、大活动系统。

### 2.3 以现有后端对象为基础扩展

当前项目里已经有不少后台可复用的基础：

- `users`
- `publish_drafts`
- `audit_records`
- `report_tickets`
- `comments`
- `media_assets`
- `async_task_records`
- `feed_items`

后台设计应尽量复用这些对象，不另起一套平行数据。

## 3. 后台需要管理的核心对象

结合现有社区，后台至少需要管这几类对象：

### 3.1 账号与角色

- 普通用户
- 创作者
- 审核员
- 运营
- 管理员

### 3.2 内容对象

当前主内容明确分 3 类：

1. 提示词内容
   - 视频提示词
   - 图片提示词
2. 工作流内容
3. 帖子内容

### 3.3 互动对象

- 评论
- 点赞/收藏相关异常行为
- 举报工单

### 3.4 运营对象

- 首页 hero
- 首页各内容区
- 精选页排序
- 讨论区置顶与排序
- 后续活动位、专题位

### 3.5 资源与任务对象

- 图片/视频媒体资源
- 封面、poster、preview
- 上传回调
- 异步任务
- OSS 资源状态

## 4. 第一版后台建议模块

## 4.1 后台登录与权限

这是后台的入口模块，优先级最高。

建议能力：

- 后台独立登录
- 后台角色权限控制
- 页面级权限控制
- 操作级权限控制
- 操作审计日志

建议角色先收口成：

- `admin`
- `operator`
- `moderator`

说明：

- `admin`：系统级管理
- `operator`：首页/精选/专题/排序等运营操作
- `moderator`：审核、举报、评论处理

## 4.2 账号管理

这就是你现在最先想到的那块，也是必须有的。

建议能力：

- 新增账号
- 删除账号
- 重置密码
- 修改角色
- 禁用/启用账号
- 查看账号基础信息
- 查看账号发布内容数量
- 查看账号违规/举报历史

建议补充：

- 不建议物理删除，优先软删除或禁用
- 后续登录切公司统一体系后，这里更偏“账号状态管理 + 角色授权”，而不是完全自己管认证

## 4.3 内容审核中心

这是后台第一版最核心模块之一。

建议把审核对象统一进一个“内容审核中心”，但支持筛选不同内容类型。

审核对象：

- 视频提示词
- 图片提示词
- 工作流
- 帖子

建议能力：

- 待审核列表
- 已通过列表
- 已驳回列表
- 已下线列表
- 按内容类型筛选
- 按作者筛选
- 按时间筛选
- 审核备注
- 审核通过
- 审核驳回
- 手动下线
- 手动恢复

建议审核字段统一：

- 内容类型
- 内容标题
- 作者
- 标签
- 当前状态
- 风险提示
- 提交时间
- 审核人
- 审核意见

## 4.4 评论与举报处理中心

后续评论和帖子要加举报功能，这一块建议不要分散做，直接放后台统一治理。

建议分两部分：

### A. 评论治理

- 查看最新评论
- 查看被举报评论
- 删除评论
- 隐藏评论
- 查看楼中楼上下文
- 查看评论所属内容
- 对某个内容关闭评论

### B. 举报工单

举报对象建议至少支持：

- 帖子
- 评论
- 提示词内容
- 工作流内容

建议工单字段：

- 举报对象类型
- 举报对象 ID
- 举报原因
- 举报说明
- 举报人
- 被举报作者
- 当前状态
- 处理人
- 处理结果
- 处理备注

建议处理动作：

- 标记无问题
- 警告
- 下线内容
- 删除评论
- 禁用账号
- 转人工复审

## 4.5 首页与精选运营配置

这是你提到的“把想要展示的视频提前”的核心模块，优先级很高。

建议做成“运营配置中心”，不要散在数据库里硬改。

第一版建议覆盖：

- 首页 hero 轮播配置
- 首页各区块内容排序
- 精选页排序
- 讨论区置顶与排序
- 指定内容设为推荐
- 指定内容取消推荐
- 手动插队
- 时间维度上下线

建议能力：

- 拖拽排序或序号排序
- 指定展示开始/结束时间
- 按内容类型选择资源
- 支持置顶、推荐、普通三个级别
- 支持运营备注

这块后续会逐步替代现在部分“写死前端展示顺序”的逻辑。

## 4.6 分类、标签、分区管理

你最近已经把前台分类体系想清楚了，这一块后台必须跟上，不然后面会越来越乱。

建议后台管理这些配置：

### 提示词分类

- 视频提示词
- 图片提示词

### 模型标签

图片模型：

- `gpt-image-2`
- `nanobanana`
- `midjourney`
- `other`

视频模型：

- `seedance`
- `kling`
- `happyhorse`
- `wan`
- `other`

### 内容母类

- 真人
- 动画
- 场景
- 道具
- 其他

### 讨论区分区

- 官方活动
- 闲聊茶水间
- 方法讨论
- 作品求助
- 后续更多板块

建议能力：

- 新增标签/分区
- 修改标签显示名
- 调整排序
- 启用/停用
- 设置是否前台可见

## 4.7 媒体资源与异步任务中心

这个模块很容易被忽略，但对你们现在非常有用。

因为现在项目已经有：

- 上传
- OSS
- 回调
- 封面/preview 生成
- 异步任务
- 媒体代理

后台如果没有任务中心，后续排查会很痛苦。

建议能力：

- 查看上传任务状态
- 查看异步任务状态
- 查看失败任务
- 查看失败原因
- 重新触发部分任务
- 查看资源绑定关系
- 查看某内容关联的封面/source/poster/preview

建议优先展示的任务：

- 视频上传
- 封面回填
- preview 生成
- 审核辅助任务
- 工作流绑定检查

## 4.8 数据概览面板

第一版不用做重 BI，但建议做一个轻量运营首页。

建议指标：

- 待审核内容数
- 待处理举报数
- 今日新增内容数
- 今日新增评论数
- 今日新增用户数
- 失败异步任务数
- 首页运营位当前数量

它的目标不是分析业务增长，而是让运营/审核一进后台就知道哪里有积压。

## 5. 第一版不建议立即重做的内容

有些后台能力可以先不急：

- 复杂推荐系统
- 搜索运营后台
- 大型活动系统
- 创作者激励结算
- 申诉中心
- 批量营销通知系统
- 多维 BI 报表

这些不是没用，而是当前阶段不该抢主线。

## 6. 推荐的后台一期优先级

建议你们后台按下面顺序做：

### P0

- 后台登录与 RBAC
- 账号管理
- 内容审核中心
- 举报处理中心
- 首页/精选/讨论区排序运营

### P1

- 标签/分区管理
- 评论治理
- 媒体与异步任务中心
- 基础数据概览

### P2

- 活动/专题运营
- 榜单配置
- 申诉与恢复中心
- 搜索与推荐配置

## 7. 和现有项目的衔接建议

为了避免后面重构太痛，后台建议沿这条线建设：

### 7.1 前端形态

- 单独一套后台前端
- 可继续用 Next.js
- 路由建议独立成 `/admin` 或单独项目

### 7.2 后端形态

- 继续复用现有 Spring Boot
- 新增 `/api/admin/**` 路由组
- 复用现有领域服务，不另起重复业务逻辑

### 7.3 权限形态

- 用户前台身份与后台角色分开看
- 前台登录用户不等于后台可操作用户
- 所有后台操作必须记操作日志

## 8. 结合当前项目，最值得补充的后台功能

除了你已经想到的几项，我认为还应该补这几项：

### 8.1 内容下线与恢复

这个很重要，尤其是后续举报处理、审核误判、活动调整时会频繁用到。

### 8.2 评论治理开关

你前台已经做了“关闭评论区”和“删除评论”，后台也应有统一入口，避免必须登录作者账号去处理。

### 8.3 运营排序历史

谁把哪个内容提到了首页、什么时候下掉、为什么调整，最好可追踪。

### 8.4 失败任务排查入口

现在你们已经开始接 OSS、异步任务、媒体回调，后台没有这个入口，后续问题都会堆到研发排查。

### 8.5 标签与分区治理

你现在很重视分类规范，这一块如果不在后台建入口，后面只能继续手改数据，成本会越来越高。

## 9. 当前建议结论

后台第一版不要做成“大而全后台”，而是先做成一套能支撑社区上线和运营的治理系统。

最先做的 5 个模块建议固定为：

1. 后台登录与 RBAC
2. 账号管理
3. 内容审核中心
4. 举报与评论治理中心
5. 首页/精选/讨论区运营排序中心

这 5 个做完，你们这个社区就不再只是“能展示内容”，而是进入“能运营、能审核、能治理、能控节奏”的状态。
