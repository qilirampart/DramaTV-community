结合你从需求沟通→日志上报→错误码映射→ELK接入的整个实战过程，我为你总结了一份开发时的避坑清单和跨部门对接SOP。

以后你在开发任何项目（尤其是AI生成类、第三方对接类）时，只要按这套流程走，效率会翻倍，线上问题会少很多。

 

🛠️ 一、开发阶段：编码前必须想清楚的 4 件事

这些是你踩过的坑对应的核心逻辑，写代码前先过一遍。

1. 日志规范：0 容忍的底线

核心原则：日志是线上排查的唯一眼睛，绝不能只打印到控制台（nohup.out）。

- 落地要求：

- 结构化输出：不要打印纯字符串，尽量用 JSON 格式，方便后期检索。

- 必备字段：每条日志必须带上  TraceID （链路追踪）和  UserID （业务定位）。

- 分类切割：必须按级别分开（ info.log  存正常流程， error.log  存报错），按时间滚动（按小时或天切割，不要堆成一个几G的大文件）。

- 你要怎么写：

- 初始化日志框架时（Logback/Log4j2/Python Logging），直接写好配置文件，把日志路径、保留天数、JSON格式定死。

2. 第三方对接：统一“错误语言”

核心原则：第三方供应商的错误码都是乱的，绝不能直接抛给用户或前端。

- 落地要求：

- 建立映射表：做一个配置表，把三方的  429 、 500 、 Error: Balance  映射到你自己的业务错误码。

- 做兜底文案：映射不到的错误，统一返回“服务繁忙，请稍后重试”，不要把原始的堆栈信息露出去。

- 你要怎么写：

- 写一个全局的异常拦截器或转换工具类。调用三方接口失败时，统一经过这个类转换，再抛出。

3. 配置化：所有可变参数写进配置

核心原则：服务器路径、日志路径、供应商ID、超时时间，绝对不要写死在代码里。

- 你要怎么考虑：

- 日志路径、配置项要通过环境变量或配置中心（Nacos/Apollo）传入。

- 这样运维能改，你不用重启服务。

4. 可观测性：先埋坑，后上线

核心原则：不要等上线挂了再排查，上线前就要想好怎么监控。

- 落地要求：

- 埋点：关键接口（如生成视频、调用三方）的入参、出参、耗时，都要打印出来。

- 告警规则：提前规划好，哪些错误率一爆就要报警（如 5xx 错误、接口 500 次数）。

 

🤝 二、跨部门（运维/产品/前端）对接SOP

以后遇到新需求，按这个流程对接，不会扯皮，效率最高。

第一步：需求确认时，先问“边界”

对接前，先确认公司已有的基建，不要自己瞎折腾：

- 问运维：“公司有没有成熟的 ELK/云日志平台（如腾讯云CLS）？如果有，接入标准是什么？如果没有，我按标准落盘后，你们需要什么格式？”

- 问运维：“服务器的日志目录有没有规范？比如统一放在  /var/log/  下吗？”

第二步：技术方案时，主动给“选项”

不要只给一个方案，给运维两个选择，让他们选，显得你专业：

- 方案 A（推荐）：接入公司现成的日志平台（如果有），你只需要把日志按规范写好。

- 方案 B（兜底）：如果没有平台，你就做本地落盘+按小时切割，并写好脚本，把日志同步到指定位置（如之前聊的网盘同步）。

第三步：开发交付时，给“证明”

代码提交前，把运维交付物准备好，不要等运维来问你要资料：

- 交付清单：

1. 日志配置表：证明日志是结构化的，路径是固定的。

2. 目录结构：发一张  ls /var/log/xxx  的截图，证明 info/error 分开，且有时间戳。

3. 示例日志：贴一条 JSON 格式的日志样例，让运维一眼就能看懂。

第四步：上线后，怎么复盘？

- 上线第一周，每天去日志平台看一眼，确认有没有报错、有没有漏网之鱼（漏网之鱼就是之前没映射到的新错误）。

- 把线上出现的新错误，更新到你的错误码映射表里。

 

📋 三、你的专属行动清单（Next Step）

现在你可以把这几个点闭环掉：

1. 日志改造：立刻把当前的日志输出改成 JSON格式 + 按小时切割 + 分类(info/error)。

2. 确认接入：拿着你做好的日志配置，去找曹学朋（运维），发给他：“我已经按标准改造好了，这是路径和示例，帮我确认下能否接入平台？”

3. 完善映射：把之前遇到的  429 、各种未知报错，全部补全到映射表中，配置好兜底文案。

总结一句话：
以后开发，日志要结构化，错误要统一化，对接要前置化。只要做到这三点，线上99%的排查难题都能解决。
